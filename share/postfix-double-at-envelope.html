Postfix accepts a MAIL FROM containing two unquoted at-signs and commits the envelope domain taken from the last one, where Exim and OpenSMTPD reject the command (Postfix ≤ 3.10.12)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Postfix project (Wietse Venema)
Software: Postfix
Affected version: Postfix 3.10.12, the current release under test. The differential peers are Exim 4.96 and OpenSMTPD, both of which reject the input Postfix accepts.
Vulnerable component: SMTP envelope address parsing in smtpd — acceptance and silent rewriting of a Mailbox whose local part contains an unquoted @
Vulnerability type: CWE-436 (Interpretation Conflict)
Attack vector: Remote, unauthenticated. One SMTP transaction with a malformed MAIL FROM argument.
CVSS v3.1: 4.0 (Medium) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:C/C:N/I:L/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Five of five deterministic across three MTAs, with the committed envelope domain read back from the delivered message's Return-Path, and the Postfix acceptance independently re-confirmed on a second host.

Impact. MAIL FROM:<admin@trusted.test@sender.test> is accepted with 250 and silently requoted to <"admin@trusted.test"@sender.test>, so SPF is keyed on sender.test while a first-at-sign parser reads trusted.test.

Description

An envelope-domain split across parsers. For <admin@trusted.test@sender.test>, Postfix keys the envelope — and therefore the SPF check and the SPF-aligned DMARC identity — on sender.test, while any component that splits on the first @ attributes the message to trusted.test. In a mixed chain, where Postfix sits behind or in front of a perimeter appliance, a content filter, a reputation service or a log pipeline with a different address parser, one component authorises or reputes a domain other than the one Postfix actually authenticated.

The practical consequence is attribution confusion rather than a demonstrated authentication bypass: a filter that trusts trusted.test may exempt a message whose SPF was in fact evaluated for an unrelated domain, and logs and reports may name a domain that took no part in the authentication decision. Accepting the command at all is also a plain interoperability divergence, since messages Postfix admits are refused by Exim and OpenSMTPD.

RFC 5321 section 4.1.2 defines Local-part = Dot-string / Quoted-string. A bare unquoted @ is not atext, so <a@b@c.test> is not a legal Mailbox and the command carrying it is not a legal MAIL command.

Postfix accepts it with 250. It resolves the ambiguity by taking the last @ as the delimiter, quotes the prefix, and commits the envelope sender as <"a@b"@c.test> — envelope domain c.test. Exim replies 501 and OpenSMTPD 553. Exim's error text names the defect class precisely: “malformed address: @c.test> may not follow <a@b”.

The same raw MAIL FROM bytes were offered to each MTA, and Postfix's committed envelope domain was read back from the Return-Path of the delivered message:

The control row is what makes the rest meaningful: all three MTAs accept a well-formed Mailbox, so the rejections in the other rows are specific to the malformed input and not an artefact of the transport used to deliver it. Five of five were deterministic.

Two properties of Postfix's handling are worth separating. The first is leniency: it accepts a string two other widely deployed MTAs reject. The second, and the one with security relevance, is that it does not merely accept the string but silently rewrites it into a form whose meaning is different from the reading another parser would take, and then uses that meaning for SPF and for the DMARC SPF-aligned identity.

Proof of Concept

Offer the malformed command as raw bytes, so that no client library normalises it first:

EHLO probe.test
MAIL FROM:<admin@trusted.test@sender.test>
250 2.1.0 Ok                      <- Postfix
                                     Exim:      501 malformed address
                                     OpenSMTPD: 553 syntax error
RCPT TO:<user@receiver.test>
DATA
From: admin@trusted.test
To: user@receiver.test
Subject: invoice

...
.

Required under RFC 5321 section 4.1.2: the command is rejected, because the local part contains an unquoted @ and is therefore neither a Dot-string nor a Quoted-string. Observed on Postfix: 250, and the delivered message carries the committed envelope sender

Return-Path: <"admin@trusted.test"@sender.test>

so that Postfix evaluates SPF for sender.test. Any component in the path that splits on the first @ instead reads trusted.test. That disagreement, and Postfix's committed choice of sender.test, is what the laboratory demonstrates.

Mitigation

Reject a MAIL FROM whose Mailbox contains an unquoted @ in the local part, with a 501, as Exim and OpenSMTPD do. That is what RFC 5321 section 4.1.2 requires and it removes the ambiguity at the point where it enters the system.

If leniency is retained deliberately for compatibility, the rewriting is the part to reconsider: committing a requoted address whose domain differs from the one a first-@ reader derives converts a malformed input into a durable disagreement between components. At a minimum the rewrite should be logged in a form that lets an operator see both readings.

Notes

What is and is not demonstrated. The single-hop laboratory shows two things: the accept-versus-reject split across the three MTAs, and the envelope domain Postfix commits. It does not show an end-to-end exploit. Making this into a bypass requires a mixed-MTA chain in which another component reads the first @ and acts on it, and that chain was not built or measured here. No demonstrated authentication bypass is claimed, and the severity above reflects that.

A methodological note on the evidence. An ad-hoc re-verification of the Exim and OpenSMTPD rejections through a client library was confounded: that path emits a MAIL FROM in a form both MTAs reject generically, so it cannot distinguish an address-specific parse error from a generic one. The reliable evidence is the raw-byte SMTP transcript, which produced the address-specific errors quoted above, including Exim's message naming the two at-signs.

Two open questions for the vendor: whether smtputf8 or address rewriting alters the committed domain, and whether the same last-@ rule applies on the RCPT TO side.
