OpenDMARC computes an over-broad organisational domain under a Public Suffix List wildcard rule, letting a co-tenant host spoof its neighbour (OpenDMARC ≤ 1.4.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDMARC
Source code: https://github.com/trusteddomainproject/OpenDMARC
Affected version: OpenDMARC 1.4.2, built from the upstream tarball rel-opendmarc-1-4-2. The finding was originally isolated on the Debian package 1.4.2-1+deb12u1 and re-confirmed against pristine upstream. Earlier 1.4.x and 1.3.x releases are expected to share the behaviour.
Vulnerable component: DMARC organisational-domain computation from the Public Suffix List, under a wildcard (*) rule
Vulnerability type: CWE-346 (Origin Validation Error) leading to CWE-290 (Authentication Bypass by Spoofing)
Attack vector: Remote. The attacker must control one host under the same wildcard suffix as the victim, which on shared cloud infrastructure means renting an instance.
CVSS v3.1: 6.5 (Medium) — CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. The wildcard rule was verified byte-identical in both verifiers' Public Suffix List files, so the divergence is an algorithm defect and not a data difference.

Impact. Under a rule such as *.compute.amazonaws.com, OpenDMARC stops one label short, so any sibling host's DKIM signature relaxed-aligns with the victim.

Description

On shared wildcard infrastructure — AWS EC2 *.compute.amazonaws.com, *.elasticbeanstalk.com, *.r.appspot.com and the many similar entries in the Public Suffix List — an attacker who controls one host under the wildcard can spoof a co-tenant past OpenDMARC under p=reject; adkim=r. Obtaining such a host is a matter of renting an instance, so the practical barrier is low even though the CVSS vector records it as a privilege requirement.

The wildcard entries exist in the Public Suffix List precisely to keep such tenants in separate organisations, so this defeats the isolation the list is there to provide.

A Public Suffix List wildcard rule such as *.compute.amazonaws.com makes tenanta.compute.amazonaws.com itself a public suffix. The registrable, that is organisational, domain of x.tenanta.compute.amazonaws.com is therefore the full name: public suffix plus one label.

OpenDMARC stops at the wildcard-matched suffix and computes the organisational domain as tenanta.compute.amazonaws.com — one label short. Every host under that wildcard child is then treated as sharing an organisation with every other, so under relaxed alignment a DKIM signature from any sibling host aligns with the victim's From domain.

With From=x.tenanta.compute.amazonaws.com and _dmarc.x.tenanta.compute.amazonaws.com publishing v=DMARC1; p=reject; adkim=r:

DKIM d=OpenDMARCRspamdRequired
z.tenanta.compute.amazonaws.com (sibling host, a distinct registrable domain)pass — bypassrejectreject
z.tenantb.compute.amazonaws.com (a different wildcard child, control)failfailfail
plain.compute.amazonaws.com (one level up, control)failfailfail

The two controls bound the defect precisely. OpenDMARC collapses to tenanta.compute.amazonaws.com and not all the way to amazonaws.com, so the error is exactly one label and it makes siblings under the same wildcard child, and only those, wrongly share an organisation.

The Public Suffix List data is not the cause. OpenDMARC reads /usr/share/publicsuffix/public_suffix_list.dat and Rspamd reads /usr/share/rspamd/effective_tld_names.dat, which are different files, but *.compute.amazonaws.com is byte-identical in both, and computing the canonical registrable domain with the publicsuffixlist library over each container's own file agrees with Rspamd. The divergence is therefore in OpenDMARC's label counting.

Proof of Concept

# zone
_dmarc.x.tenanta.compute.amazonaws.com.  IN  TXT  "v=DMARC1; p=reject; adkim=r"

# attacker publishes a DKIM key for the host they control
sel._domainkey.z.tenanta.compute.amazonaws.com.  IN  TXT  "v=DKIM1; k=rsa; p=..."

Send a message with From: ceo@x.tenanta.compute.amazonaws.com, signed d=z.tenanta.compute.amazonaws.com with the attacker's own valid key. Required: dmarc=fail, since the two are distinct registrable domains and cannot align even under adkim=r. Observed on OpenDMARC: dmarc=pass.

Mitigation

When the matched Public Suffix List rule is a wildcard, the public suffix includes the label the wildcard matched. The organisational domain is that suffix plus one further label. Add the wildcard's matched label to the count before taking the registrable domain.

Notes

Pairs with rspamd-psl-rules-ignored, in which Rspamd mishandles the same class of rules in the opposite direction. Distinct from psl-snapshot-drift, which is a data-freshness divergence between the two vendored lists rather than an algorithm defect.

The laboratory's example.com-as-public-suffix fixture was deliberately not used for this test; no example.com name appears anywhere in the reproduction.
