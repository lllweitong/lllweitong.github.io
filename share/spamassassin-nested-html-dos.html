Apache SpamAssassin quadratic-time denial of service on deeply nested HTML (Apache SpamAssassin 3.4.6)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Apache Software Foundation (Apache SpamAssassin)
Software: Apache SpamAssassin
Source code: https://github.com/apache/spamassassin
Affected version: 3.4.6 (the version tested). Other releases sharing the same HTML processing are likely affected; not yet verified against 4.x.
Vulnerable component: HTML body processing — Mail::SpamAssassin::HTML and its HTML::Parser usage; the exact quadratic loop is not yet pinpointed.
Vulnerability type: CWE-407 (Inefficient Algorithmic Complexity)
Attack vector: Remote, unauthenticated. One inbound e-mail; SpamAssassin scans the HTML body of every message.
CVSS v3.1: 7.5 (High) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H
Status: Confirmed by timing measurement across four nesting depths, with a flat-body control that isolates depth from size.

Impact. A 220 KB message body of nested <div> elements occupies the scanner for over a minute; doubling the nesting depth quadruples the time.

Description

An availability issue in mail processing rather than a crash. Under the default per-message timeout, a stream of such messages backs the queue up and stalls delivery; without an effective timeout the scanner occupies a core per message for minutes. The cost to the attacker is one 220 KB message, so the amplification is substantial and the attack requires no authentication and no prior relationship with the target.

SpamAssassin's HTML processing scales quadratically in the nesting depth of the message body. A body consisting of deeply nested <div> elements occupies the scanner for minutes, while a flat body many times larger scans in seconds. Because the body is fully attacker-controlled and every inbound message is scanned, one moderately sized message can stall mail processing.

Timing across nesting depths, with the message size shown for each:

Nested <div> depthScan timeMessage size
2,0003.2 s~22 KB
5,0007.9 s~55 KB
10,00031.8 s~110 KB
20,000> 60 s (timeout)~220 KB

Doubling the depth from 5,000 to 10,000 quadruples the time, from 7.9 s to 31.8 s, which is the signature of an O(n²) algorithm.

The control isolates depth from byte count: a flat 2 MB body — roughly ten times the size of the 220 KB nested case — scans in about 4 seconds. The cost is therefore the tree depth, not the volume of input, which rules out ordinary large-input slowness.

Proof of Concept

printf 'From: a@b.com\nContent-Type: text/html\n\n' > poc
python3 -c "import sys; sys.stdout.buffer.write(b'<div>'*20000 + b'x' + b'</div>'*20000)" >> poc

time spamassassin --local -t < poc     # > 60 s on a ~220 KB message

Reduce the repetition count to 10,000 for a reproduction that completes, at roughly 32 seconds.

Mitigation

Bound the work rather than the input alone:

  • Impose a maximum HTML nesting depth during parsing and stop descending beyond it.
  • Apply a body and HTML size limit in Mail::SpamAssassin configuration.
  • Enforce a per-message CPU cap so that a pathological body cannot consume unbounded time.

Root-causing the specific quadratic loop — whether it is in the tree construction or in a rule that walks the tree per node — is the next step and would allow a targeted fix rather than a limit.

Notes

Check for a duplicate before submission. SpamAssassin has prior denial-of-service CVEs, including CVE-2017-15705 and CVE-2018-11780. Whether this specific nested-HTML quadratic is already covered by an existing assignment has not been established, and should be checked with the Apache SpamAssassin security team before a new identifier is requested.

Tested against 3.4.6 only. Confirmation against the current 4.x line is outstanding.
