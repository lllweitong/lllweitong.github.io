Rspamd ignores Public Suffix List exception and wildcard rules, so registrants under those rules have DMARC silently unenforced (Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Rspamd project (Vsevolod Stakhov)
Software: Rspamd
Affected version: Rspamd 4.1.2. Originally isolated on 3.10.2 and re-confirmed on 4.1.2 on 2026-07-28.
Vulnerable component: DMARC organisational-domain computation (get_tld and the Public Suffix List handling in dmarc.lua)
Vulnerability type: CWE-346 (Origin Validation Error) leading to CWE-290 (Authentication Bypass by Spoofing)
Attack vector: Remote, unauthenticated. One forged, unaligned message against any registrant under such a rule.
CVSS v3.1: 7.5 (High) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. The rules were verified byte-identical in both verifiers' Public Suffix List files, so the divergence is an algorithm defect and not a data difference.

Impact. For a name under *.kawasaki.jp with the exception !city.kawasaki.jp, Rspamd queries the wrong _dmarc node and reports no policy.

Description

Every registrant under a Public Suffix List * or ! construct has its p=reject or p=quarantine silently unenforced on Rspamd receivers. Forged mail in the registrant's name is delivered while conforming verifiers reject it.

As with several findings in this set, the registrant has no way to detect the loss of protection: their own aligned mail continues to be delivered normally, and no reports show the forgeries.

The Public Suffix List rules *.kawasaki.jp together with the exception !city.kawasaki.jp make the registrable domain of foo.city.kawasaki.jp equal to city.kawasaki.jp. That is where the registrant publishes its DMARC policy.

Rspamd does not apply the * and ! constructs. It computes the organisational domain as the full From domain, foo.city.kawasaki.jp, queries the non-existent _dmarc.foo.city.kawasaki.jp, finds nothing, and returns DMARC_NA — no policy. The forgery is delivered.

With From=foo.city.kawasaki.jp, a forged unaligned message (DKIM d=attacker, SPF -all), and the registrant publishing p=reject at its true organisational node _dmarc.city.kawasaki.jp:

OpenDMARCRspamdRequired
forged, unaligned messagefail, disposition rejectnone / DMARC_NA — deliveredreject

Rspamd's own log option gives the computed value directly — DMARC_NA{foo.city.kawasaki.jp} — and the absent node it queried confirms it never consulted _dmarc.city.kawasaki.jp.

Scope of the defect. A static, deeply nested suffix such as pvt.k12.ma.us is handled correctly by Rspamd, with both verifiers agreeing on alpha.pvt.k12.ma.us and both rejecting. The defect is therefore specific to the * and ! constructs, not to multi-label depth.

The Public Suffix List data is not the cause. Both *.kawasaki.jp and !city.kawasaki.jp are byte-identical in the two containers' list files, and the canonical registrable domain computed from either file agrees on city.kawasaki.jp.

Proof of Concept

# zone: the registrant's real policy, at its true organisational node
_dmarc.city.kawasaki.jp.  IN  TXT  "v=DMARC1; p=reject; sp=reject"
# _dmarc.foo.city.kawasaki.jp does not exist

Send a forged, unsigned message from an unrelated host with From: ceo@foo.city.kawasaki.jp and an envelope sender in another domain. Required: dmarc=fail, disposition reject. Observed on Rspamd: DMARC_NA, delivered. OpenDMARC on the identical message rejects.

Mitigation

Implement the Public Suffix List algorithm completely in get_tld: a wildcard rule *.x extends the public suffix by the matched label, and an exception rule !y.x removes y.x from the suffix set so that y.x is itself registrable. Exception rules take priority over wildcard rules.

Notes

Pairs with opendmarc-psl-wildcard-orgdomain, the same family of rules mishandled by OpenDMARC in the opposite direction. Between them the two verifiers cover both failure modes, so a domain under such a rule is unprotected on one receiver or the other depending on which it is.
