Rspamd returns SPF pass instead of permerror when the DNS lookup limit is exceeded, bypassing SPF authorisation (Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Rspamd project (Vsevolod Stakhov)
Software: Rspamd
Affected version: Rspamd 4.1.2. Originally isolated on 3.10.2 and re-confirmed on 4.1.2 on 2026-07-28.
Vulnerable component: SPF module — the DNS-lookup processing limit, in the parse_spf_include path
Vulnerability type: CWE-755 (Improper Handling of Exceptional Conditions) leading to CWE-290 (Authentication Bypass by Spoofing)
Attack vector: Remote, unauthenticated. The attacker publishes the SPF record at a domain they control.
CVSS v3.1: 7.5 (High) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. A 22-case sweep with boundary and negative controls, plus a root-cause log line.

Impact. Padding an SPF record with eleven or more lookups before an authorising ip4 makes Rspamd skip the limit and return pass.

Description

An SPF authorisation bypass. The attacker publishes eleven or more padding lookups, or a self-include loop, before an ip4 that authorises their sending host. A conforming verifier returns permerror, meaning no authorisation was established; Rspamd returns pass.

The consequence carries into DMARC: under aspf=r an SPF pass aligned with the From domain produces dmarc=pass, so a message that should have had no SPF authorisation at all becomes a DMARC-authenticated message. The processing limit exists specifically to prevent crafted records from steering evaluation, which is the case section 11.1 calls out.

RFC 7208 section 4.6.4 is a MUST: an implementation must limit the DNS-querying terms (include, a, mx, ptr, exists, redirect) to ten, and “if this limit is exceeded, the implementation MUST return permerror”. Section 11.1 names crafted limit-exceeding records as precisely the attack this defends against, and section 5.2 requires an include that evaluates to permerror to propagate it.

Rspamd treats “lookup limit exceeded inside a term” as a soft skip of that term and carries on evaluating left to right. A later authorising ip4 then matches and the result is pass.

The debug log is unambiguous — the limit is detected and then the record authorises anyway:

parse_spf_include: spf dns requests limit: 31 > 30 is reached
...
R_SPF_ALLOW{+ip4:203.0.113.7}

The controls hold throughout. A ten-lookup chain with an authorising terminal passes on both, so the rig genuinely authorises within budget; the same chain with -all fails on both; and a non-matching deep IP on the self-loop makes Rspamd return fail, which proves the pass genuinely originates from the post-limit ip4 rather than from a loop-handling default.

OpenDMARC's own ceiling is approximately eleven terms rather than the specified ten, but it does enforce a ceiling and fails closed past it. Rspamd enforces no ceiling in the matching path, up to its unrelated 30-request denial-of-service guard.

Proof of Concept

Publish, at a domain the attacker controls:

attacker.example.  IN  TXT  "v=spf1 exists:a1.%{d} exists:a2.%{d} exists:a3.%{d}
                              exists:a4.%{d} exists:a5.%{d} exists:a6.%{d}
                              exists:a7.%{d} exists:a8.%{d} exists:a9.%{d}
                              exists:a10.%{d} exists:a11.%{d} exists:a12.%{d}
                              ip4:203.0.113.7 -all"

with all twelve exists targets NXDOMAIN, then send mail from 203.0.113.7. The self-include form works equally well:

attacker.example.  IN  TXT  "v=spf1 include:attacker.example ip4:203.0.113.7 -all"

Required: permerror, that is, no SPF authorisation. Observed on Rspamd: spf=pass / R_SPF_ALLOW.

Mitigation

When the querying-term budget is exhausted inside a term, abort the whole evaluation and return permerror, rather than skipping the term and continuing. Propagate permerror out of a nested include per section 5.2, and set the limit at ten as specified.

Notes

A separate consensus gap, recorded but not claimed as a divergence: the void-lookup limit (section 4.6.4, at most two NXDOMAIN or NODATA lookups before permerror) is unenforced on both verifiers. That is a shared weakness rather than a difference between them.

Rspamd skips SPF entirely for a private connecting address, so the test rig supplied a public ip=; the sender domain was regenerated per run because Rspamd caches SPF results for 300 seconds.
