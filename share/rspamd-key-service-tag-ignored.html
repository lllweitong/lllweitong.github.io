Rspamd ignores the DKIM key record's s= service-type tag, so a key scoped to a non-email service still signs email (Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Rspamd project (Vsevolod Stakhov)
Software: Rspamd
Source code: https://github.com/rspamd/rspamd
Affected version: Rspamd 4.1.2. Originally isolated on 3.10.2 and re-confirmed on 4.1.2 on 2026-07-28. OpenDKIM 2.11.0 and dkimpy 1.1.8 both enforce the tag correctly.
Vulnerable component: DKIM public-key record handling — the s= service-type tag of RFC 6376 section 3.6.1
Vulnerability type: CWE-347 (Improper Verification of Cryptographic Signature) / CWE-20 (Improper Input Validation)
Attack vector: Remote. The victim key record must declare a non-email service type, and the attacker must present a signature made with that key.
CVSS v3.1: 3.7 (Low) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Three deterministic repetitions with s=email, s=* and s=email:tlsrpt controls, independently re-verified with dkimpy as a third oracle.

Impact. A key record published as s=tlsrpt, which must be ignored for email, still yields R_DKIM_ALLOW on Rspamd where OpenDKIM and dkimpy both reject it.

Description

The s= tag exists so that an operator can confine a key to one use. A key provisioned for a reporting or other non-mail service, and deliberately marked as such, is meant to be unusable for signing email even if its private half is exposed to a system that has no business signing mail. On Rspamd that scoping has no effect, and any signature made with such a key is accepted as a valid email signature.

The bound on this is the same as for the other key-record findings and is stated plainly: the party publishing s= is the party that owns the key, so the missing check does not let an attacker forge a signature for a domain they do not control. What it removes is the operator's ability to compartmentalise key material by purpose, which is precisely the defence-in-depth measure the tag provides. The compromise of a narrowly scoped non-mail key becomes a mail-signing capability on any Rspamd receiver, and on no conforming one.

RFC 6376 section 3.6.1 defines the key record's s= tag as the service type for which the key may be used, with a default of * meaning all services, and states: “Verifiers for a given service type MUST ignore this record if the appropriate type is not listed.” Email DKIM verification is service type email. A record listing only a non-email service, or an unknown one, must therefore be ignored when verifying mail, leaving no usable key and making the signature fail.

Rspamd never reads the tag. Its DKIM verdict is invariant to the content of s=, so a key deliberately scoped away from email still returns R_DKIM_ALLOW. OpenDKIM rejects the same record with the reason not an e-mail key, and dkimpy raises a ValidationError.

The same valid RSA signature is used throughout; only the key record's s= tag varies:

Key record s=OpenDKIMRspamddkimpyRequired
s=email (control)passR_DKIM_ALLOWpasspass
s=* (control, the RFC default)passR_DKIM_ALLOWpasspass
s=tlsrpt (a non-email service)fail, reason="not an e-mail key"R_DKIM_ALLOWfail (ValidationError)fail
s=foo (an unknown service)failR_DKIM_ALLOWfailfail

OpenDKIM's own reason string names the cause exactly, and dkimpy fails independently, so two implementations agree on the required verdict. The list form s=email:tlsrpt passes on all three, which is correct, because email is listed. Rspamd's verdict is identical in every row, which is the direct evidence that the tag is not consulted rather than parsed and mishandled.

The s=foo row matters as much as the s=tlsrpt row. An unknown service type is not a special case to be tolerated: section 3.6.1 requires the verifier to ignore any record whose listed types do not include its own, so an unrecognised value must make the record unusable for email rather than be treated as permissive.

Proof of Concept

Publish a key record scoped to a non-email service:

sel._domainkey.signer.example.  IN TXT "v=DKIM1; k=rsa; s=tlsrpt; p=<base64 RSA public key>"

Sign an ordinary message with the matching private key:

DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=signer.example; s=sel;
    h=from:to:subject:date; bh=<body hash>; b=<signature>

Required under RFC 6376 section 3.6.1: the record does not list the email service type, so an email verifier must ignore it, leaving no key and failing the signature. Observed on Rspamd: R_DKIM_ALLOW. Observed on OpenDKIM: dkim=fail with reason="not an e-mail key". Observed on dkimpy: ValidationError.

Replacing s=tlsrpt with s=email, s=* or s=email:tlsrpt makes all three implementations pass, which isolates the service-type tag as the only variable.

Mitigation

Compare the record's s= list against the verifying service before using the key, applying the RFC 6376 section 3.6.1 default of * when the tag is absent, and treat the record as unusable when email is not listed. An unknown or unparseable service type must make the record unusable for email rather than be treated as permissive.

Notes

Part of the Rspamd DKIM key-record constraint cluster together with rspamd-key-hash-list-ignored (the h= hash list) and rspamd-auid-subtree-unchecked (the i= AUID subtree check). The three share a single shape, namely a constraint the verifier is required to apply and does not, and they would be sensibly disclosed and fixed together.

Deployment of a non-default s= is uncommon, which bounds field exposure without affecting the conformance claim. Confirmation against upstream rspamd_dkim remains an open step; the divergence recorded here is behavioural.
