OpenDKIM ignores the DKIM key record's k= key type and takes the algorithm from the signature's a= tag, verifying an ed25519 signature against a record declared rsa (OpenDKIM ≤ 2.11.0)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDKIM
Source code: https://github.com/trusteddomainproject/OpenDKIM
Affected version: OpenDKIM 2.11.0 (Debian package 2.11.0~beta2-9.1+b1). Rspamd 4.1.2 and dkimpy 1.1.8 both reject the same records correctly.
Vulnerable component: DKIM public-key record handling — the k= key-type tag of RFC 6376 section 3.6.1 and its binding to the signature algorithm
Vulnerability type: CWE-347 (Improper Verification of Cryptographic Signature) / CWE-757 (Selection of Less-Secure Algorithm During Negotiation)
Attack vector: Remote. The signature algorithm is chosen by whoever signs; the key record is published by the key owner. No interaction with a third party is required.
CVSS v3.1: 3.7 (Low) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Confirmed three ways, with Rspamd and dkimpy as independent oracles, three stable repetitions, and a negative control in which the key bytes themselves are wrong.

Impact. A key record with no k= tag, which defaults to rsa, still verifies an ed25519-sha256 signature on OpenDKIM, where Rspamd and dkimpy both permfail.

Description

This is a conformance and robustness fail-open, not a victim-spoofing bypass, and it should not be reported as one. The party that publishes the k= and p= record is the same party that produces the signature, namely the owner of the signing domain, so ignoring k= does not enable an attacker to forge a signature for a domain they do not control. Any dmarc=pass that follows is for the signer's own aligned domain, which that signer could equally have obtained by publishing a correct k=ed25519 record.

Two concrete effects remain. The first is silent interoperability divergence: a domain whose record still says k=rsa after an ed25519 migration, or whose k= and p= otherwise disagree, is DKIM-authenticated on OpenDKIM receivers and unauthenticated on Rspamd, dkimpy, Gmail and any other conforming verifier, with no signal to the operator that the two populations disagree about their mail. The second is the loss of a defence-in-depth control: the key record's ability to restrict a key to one algorithm is unenforced, which matters exactly during an algorithm-agility transition, when a stale declaration is most likely to be present.

RFC 6376 section 3.6.1 defines k= as the key type, with a default of rsa, and states that the semantics of the p= public-key data are defined by it. RFC 8463 section 3 binds ed25519-sha256 signatures to key records declaring k=ed25519. A verifier must therefore check the algorithm implied by the signature's a= tag against the type the record declares, and reject the pair when they disagree, as RFC 6376 section 6.1.2 requires of key data unsuitable for the algorithm.

OpenDKIM does not consult k= at all. It selects the algorithm purely from the signature's a= tag and interprets the p= bytes as that algorithm's key. A record that declares k=rsa, or that declares nothing and therefore defaults to rsa, verifies an ed25519 signature and returns dkim=pass.

The message and the p= key data are identical in every row: the same correct ed25519 public key. Only the record's k= declaration and the signature's a= tag vary:

The third row is the cleanest statement of the defect. The record never names ed25519 anywhere, and under section 3.6.1 it therefore declares an RSA key, yet OpenDKIM verifies an ed25519 signature against it and reports the message as DKIM-authenticated. The fourth row shows the defect is symmetric: a record declaring k=ed25519 whose p= holds RSA key data verifies an RSA signature just as happily.

A negative control establishes that the cryptography is still genuinely performed. A k=rsa record carrying a different ed25519 public key in p= fails on OpenDKIM as well. Only the k= declaration is ignored; the signature is still checked against the key bytes that are published. OpenDKIM is the lone outlier here, with both Rspamd and the dkimpy reference implementation rejecting the mismatched records as section 6.1.2 requires.

Proof of Concept

Publish a key record that carries an ed25519 public key but declares no key type, so that the RFC default of rsa applies:

sel._domainkey.signer.example.  IN TXT "v=DKIM1; p=<base64 ed25519 public key>"

Sign the message with the matching ed25519 private key:

DKIM-Signature: v=1; a=ed25519-sha256; c=relaxed/relaxed; d=signer.example; s=sel;
    h=from:to:subject:date; bh=<body hash>; b=<signature>

Required under RFC 6376 section 3.6.1 with RFC 8463 section 3: the record declares an RSA key by default, the key data is unsuitable for ed25519-sha256, and the verifier must fail. Observed on OpenDKIM: dkim=pass with header.a=ed25519-sha256. Observed on Rspamd: R_DKIM_PERMFAIL. Observed on dkimpy: verification fails.

The explicit form "v=DKIM1; k=rsa; p=<base64 ed25519 public key>" behaves identically. Substituting a different ed25519 key in p= makes OpenDKIM fail, which is the control proving that the signature check itself still runs.

Mitigation

Determine the key type from the record's k= tag, applying the RFC 6376 section 3.6.1 default of rsa when the tag is absent, and reject the signature when the algorithm implied by a= does not match that type, per section 6.1.2 and RFC 8463 section 3. The algorithm must be derived from the key record and merely confirmed by the signature, not the other way round.

Notes

The framing here is deliberately narrower than the initial triage. An early note described this as a full DKIM and DMARC bypass; that framing is withdrawn, because the observed dmarc=pass is for the signer's own aligned domain, and no victim-spoofing scenario follows from ignoring k=.

An earlier laboratory lead recorded a k=ed25519-versus-RSA mismatch as RFC-ambiguous and did not promote it. The no-k= case in the table above removes the ambiguity, because the default of rsa is stated in section 3.6.1 and requires no interpretation.

A harness caveat that matters for anyone reproducing this: OpenDKIM's Authentication-Results value must be parsed after unfolding, because the dkim= token can sit on a folded continuation line, and Rspamd's R_DKIM_PERMFAIL symbol must be read directly rather than through a client wrapper that collapses it. Both were corrected in the reproducer before the result was recorded.

Confirmation against OpenDKIM HEAD, and identification of the point at which a= is used without consulting the record's k=, remain open steps.
