OpenDKIM evaluates only the first three DKIM signatures, so three prepended signatures bury a valid aligned one and DMARC fails (OpenDKIM <= 2.11.0 and OpenDMARC ≤ 1.4.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDKIM (feeding OpenDMARC)
Source code: https://github.com/trusteddomainproject/OpenDKIM
Affected version: OpenDKIM 2.11.0 (Debian package 2.11.0~beta2-9.1+b1). Evaluated in a milter chain with OpenDMARC 1.4.2. The laboratory configuration sets no signature-limit directive of any kind, so the cap observed is the default behaviour of the release.
Vulnerable component: DKIM multi-signature evaluation — the positional cap on how many DKIM-Signature header fields are verified
Vulnerability type: CWE-755 (Improper Handling of Exceptional Conditions) leading to denial of validation
Attack vector: Remote. The attacker needs a position from which header fields can be prepended to the victim's message — a relaying or forwarding hop, a mailing list, or a machine-in-the-middle — together with a valid DKIM key for a throwaway domain of their own. A benign chain that simply accumulates signatures reaches the same state with no attacker at all.
CVSS v3.1: 7.5 (High) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. A positional cutoff probe in which the valid signature is byte-identical in every row, an amended probe using cryptographically valid prefix signatures, and an independent dkimpy check confirming that the buried signature is both valid and aligned.

Impact. An attacker holding a valid key for a throwaway domain prepends three signatures, pushing the victim's own aligned signature out of the evaluated window, and OpenDMARC returns dmarc=fail under the victim's p=reject.

Description

This is an attacker-triggerable denial of validation, and it fails closed. Under the victim's own p=reject with RejectFailures enabled, the victim's genuine, correctly signed mail is rejected or quarantined at every OpenDMARC receiver, while Rspamd-class and Gmail-class receivers deliver it.

The cost to the attacker is low. Because the cap counts cryptographically valid signatures, no malformed-header craft is required and no key of the victim's is needed: a valid DKIM key for a domain the attacker registers is sufficient. DKIM-Signature fields are prepended at the top of the header block and DKIM is explicitly designed to survive intermediary hops, so any relaying position suffices to add them.

The suppression is silent in both directions. The sender sees ordinary delivery failures and the receiving operator sees an apparently legitimate dmarc=fail, so neither party has a signal pointing at the cap. The same state is reached accidentally by benign chains that accumulate an author signature plus several forwarder or list re-signatures.

RFC 7489 section 6.6.2 evaluates DMARC over the authenticated identifiers described in section 3.1.1: the message passes if any DKIM signature both verifies and is aligned with the RFC5322.From domain. A message may legitimately carry several DKIM-Signature header fields — multiple selectors, a forwarder re-signing, a list re-signing — and RFC 6376 section 6.1 expects a verifier to work through them.

OpenDKIM evaluates only the first three. A valid, aligned signature sitting at position four or lower is never checked; OpenDKIM stamps it dkim=neutral, which means unevaluated rather than invalid, and OpenDMARC consequently returns dmarc=fail even though a perfectly good aligned signature is present in the message. Rspamd evaluates further and returns dmarc=pass on the identical bytes.

The first probe prepends k broken aligned signatures ahead of one valid aligned signature. The valid signature is identical in every row; only the number of signatures ahead of it changes:

The flip happens exactly when the valid signature becomes the fourth. With the valid signature first and the broken ones after it, OpenDMARC passes, so the behaviour is positional rather than content-dependent: only the first three signatures are evaluated.

A second probe establishes the point that matters for exploitability. The cap counts cryptographically valid signatures, not merely malformed ones, so the prefix can be built from signatures the attacker makes with a key of their own. The victim publishes p=reject and carries its own valid aligned signature; the prefix signatures are valid and unaligned, for a domain the attacker controls:

The Authentication-Results the chain writes for the three-prefix case records the mechanism directly. The attacker's own signatures are validated and the victim's is not evaluated at all:

dkim=pass     header.d=evilcorp     (three times, the attacker's own valid signatures)
dkim=neutral  header.d=victbank header.s=vsel    <- the victim's valid, aligned signature
dmarc=fail (p=reject)

The buried signature is reported neutral, that is unevaluated, and not validation-failed, which confirms a positional cap rather than a cryptographic failure. dkimpy verifies the same buried signature as valid and aligned.

Proof of Concept

Publish, for a victim domain and for a throwaway domain the attacker owns:

_dmarc.victbank.example.            IN TXT "v=DMARC1; p=reject; adkim=s; aspf=s"
vsel._domainkey.victbank.example.   IN TXT "v=DKIM1; k=rsa; p=<victim public key>"
esel._domainkey.evilcorp.example.   IN TXT "v=DKIM1; k=rsa; p=<attacker public key>"

Take a genuine message from the victim, correctly signed and aligned, and prepend three valid signatures made with the attacker's own key above the victim's:

DKIM-Signature: v=1; a=rsa-sha256; d=evilcorp.example; s=esel; ...   <- attacker, valid
DKIM-Signature: v=1; a=rsa-sha256; d=evilcorp.example; s=esel; ...   <- attacker, valid
DKIM-Signature: v=1; a=rsa-sha256; d=evilcorp.example; s=esel; ...   <- attacker, valid
DKIM-Signature: v=1; a=rsa-sha256; d=victbank.example; s=vsel; ...   <- the victim's own
From: ceo@victbank.example
To: user@receiver.test
Subject: statement

Required under RFC 7489 section 6.6.2: the victim's aligned signature verifies, so the verdict is dmarc=pass. Observed on the OpenDKIM and OpenDMARC chain: the victim's signature is stamped dkim=neutral and the verdict is dmarc=fail (p=reject). Rspamd on the identical message returns dmarc=pass. Removing one of the three prefix signatures restores dmarc=pass on OpenDMARC, which is the control that isolates the position as the only variable.

Mitigation

Do not abandon unexamined signatures in a way that changes the DMARC verdict. If a bound on the work done per message is retained as a denial-of-service defence, it should be set well above the number of signatures legitimate multi-hop mail accumulates, it should not stop at the first three, and signatures that fail to verify should not consume budget that a later valid signature needs.

Two secondary points. Whether the cap can be raised by configuration was not established, and if such a directive exists it should be documented alongside its DMARC consequence. Separately, a signature abandoned because a cap was reached should not be reported with the same neutral token used for other unevaluated cases without any indication that the verifier chose not to look at it, since that removes the only diagnostic a receiving operator could act on.

Notes

Scoped honestly: this is not a spoof and gives an attacker no way to have a forged message accepted. It suppresses legitimate mail. The direction is fail-closed throughout, and the entry is filed as a denial of validation for that reason.

Rspamd also has a cap, reached at seven signatures in the first probe, so the existence of a cap is not in itself the defect. The defect is that OpenDKIM's is three, that valid signatures beyond it change the DMARC verdict, and that the abandoned signature is reported as though it had been considered.

Two single-shot artefacts observed during the work were discarded because they did not survive three repetitions: a DNS time-to-live race in which OpenDKIM's resolver had not yet seen a freshly published key, and a folded-header truncation caused by naive duplication of a signature. Neither contributes to the result above.

This is the multi-signature analogue of the early-stop pattern seen elsewhere in this series, in which a verifier stops before reaching an input a conforming verifier would have used.
