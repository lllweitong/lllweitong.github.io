OpenDMARC always expands the SPF %{l} macro to "postmaster", bypassing per-user SPF policy (OpenDMARC ≤ 1.4.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDMARC (SPFSelfValidate)
Affected version: OpenDMARC 1.4.2, built from the upstream tarball rel-opendmarc-1-4-2. The finding was originally isolated on the Debian package 1.4.2-1+deb12u1 and re-confirmed against pristine upstream. Earlier 1.4.x and 1.3.x releases are expected to share the behaviour.
Vulnerable component: SPF macro expansion in SPFSelfValidate — the %{l} and %{s} local-part substitution
Vulnerability type: CWE-20 (Improper Input Validation) leading to CWE-290 (Authentication Bypass by Spoofing)
Attack vector: Remote, unauthenticated, but conditional: the victim domain must publish SPF using the %{l} macro.
CVSS v3.1: 5.9 (Medium) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:H/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Confirmed over five or more independent runs with fresh random domain suffixes, using the authoritative server's query log as independent ground truth.

Impact. Every sender is evaluated as postmaster, so per-local-part SPF deny entries never match and a forged local part can pass.

Description

Any domain that implements per-user SPF policy through exists:%{l}..., a standard technique described in RFC 7208 section 5.7, is bypassed on OpenDMARC. Every sender is treated as postmaster, so per-local-part deny entries never match and the mechanism resolves at postmaster._spf, or falls through to a trailing +all or ?all. The result is SPF pass and therefore DMARC pass on a forged local part.

The precondition — that the victim deploys %{l}-based SPF — is what keeps this below the unconditional findings in severity, and is reflected in the CVSS attack complexity.

RFC 7208 section 7.3 defines the macro letters l, s and o as components of the local part of the checked identity. Sections 2.4 and 4.3 define the substitution of the literal string postmaster only for a null reverse path, MAIL FROM:<>.

OpenDMARC's SPFSelfValidate always expands %{l} to postmaster, even for a non-null MAIL FROM. Every sender is evaluated as postmaster, so per-local-part policy never applies.

Victim SPF v=spf1 exists:%{l}._spf.%{d} -all, envelope MAIL FROM:<alice@victim>, policy p=reject. The only variable is where the A record is published; the authoritative server's query log records the exact name each verifier asks for:

Three controls isolate %{l} cleanly. The domain-macro form exists:%{d}._spf.%{d} passes on both, so only the local-part macro diverges. A null sender, MAIL FROM:<>, makes both query postmaster._spf, which proves OpenDMARC is wrongly applying the null-sender rule to non-null senders rather than failing to expand the macro at all. Varying the local part and setting a HELO domain different from the MAIL FROM domain leaves OpenDMARC still querying postmaster._spf, while %{d} correctly follows the MAIL FROM domain.

Proof of Concept

victim.example.                 IN TXT "v=spf1 exists:%{l}._spf.%{d} -all"
postmaster._spf.victim.example. IN A   203.0.113.9
_dmarc.victim.example.          IN TXT "v=DMARC1; p=reject"
# alice._spf.victim.example does not exist

Send from 203.0.113.9 with MAIL FROM:<alice@victim.example> and From: alice@victim.example. Required: %{l} expands to alice, the query for alice._spf.victim.example returns NXDOMAIN, -all applies, SPF fails and DMARC fails. Observed on OpenDMARC: the query goes to postmaster._spf.victim.example, matches, SPF passes and DMARC passes.

Mitigation

Expand %{l} and %{s} from the local part of the checked identity, and substitute postmaster only when the reverse path is null, per RFC 7208 sections 7.3, 2.4 and 4.3. The defect is in the local-part wiring of OpenDMARC's SPF engine.

Notes

This corrects the root cause recorded in the earlier entry opendmarc-local-part-macro-superseded. That entry reported that SPFSelfValidate “does not expand %{l}”, inferred from a setup whose A record sat at the real local part. The true behaviour is the always-postmaster substitution, which explains that entry's observed failure and reveals the fail-open direction it missed. It should be treated as superseded for the mechanism.

A secondary, interoperability-only observation on the Rspamd side: it does not URL-encode macro-special characters in the local part, so a+b queries a._spf and a=b and a non-ASCII local part abort the query. All of these resolve to SPF fail, so there is no fail-open there.
