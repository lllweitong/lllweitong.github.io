Rspamd does not implement the SPF %{p} validated-PTR macro letter and silently drops the term instead of returning permerror (Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Rspamd project (Vsevolod Stakhov)
Software: Rspamd
Affected version: Rspamd 4.1.2. Originally isolated on 3.10.2 and re-confirmed on 4.1.2 on 2026-07-28. OpenDMARC 1.4.2 SPFSelfValidate expands the macro correctly and is the differential oracle.
Vulnerable component: SPF module — macro expansion (expand_spf_macro) and the exists term evaluation path (parse_spf_exists)
Vulnerability type: CWE-755 (Improper Handling of Exceptional Conditions)
Attack vector: Remote, unauthenticated. The denial-of-validation direction needs no attacker action at all; the fail-open shape additionally requires the victim to publish a permissive fallback qualifier.
CVSS v3.1: 4.8 (Medium) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:L
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Confirmed 3 of 3 by a DNS toggle, with a swapped macro-letter control and a root-cause debug log line naming the unsupported letter.

Impact. A sender publishing exists:%{p} has the term discarded rather than expanded, so its own mail is mis-failed, and an unrecognised macro letter never reaches the permerror the specification requires.

Description

The primary consequence is denial of validation. A domain that publishes validated-PTR SPF, which section 7.2 provides for, has its own legitimate mail mis-failed on every Rspamd receiver, and under aspf alignment that SPF failure propagates into a DMARC failure for mail the domain genuinely sent.

The secondary consequence is the swallowed error. Because the term is dropped rather than escalated, the verifier reaches a verdict it has no basis for. With a permissive fallback the verdict is neutral or softfail where the specification requires permerror, and any record whose remainder authorises the sending host would be authorised on an evaluation that was never completed. That is the fail-open shape of the same defect, and it is the reason the entry is not purely an interoperability note.

RFC 7208 section 7.2 defines p as a macro letter: the validated domain name of the client IP address, that is, the result of a PTR lookup confirmed by a forward match in the manner of section 5.5. Section 7.3 states that an unrecognised macro letter is a syntax error, and a syntax error in a record MUST yield permerror.

Rspamd implements neither half. Its macro expander does not know the letter p, so the term containing it becomes unresolvable and is silently dropped from the evaluation, which then falls through to the record's all qualifier. No permerror is raised. OpenDMARC's SPFSelfValidate expands the macro, performs the query and matches.

The rig publishes PTR for 203.0.113.45 pointing at m.victim, and a forward A record for m.victim equal to 203.0.113.45, so %{p} validates to m.victim under section 5.5. The sender's record is v=spf1 exists:%{p}._chk.%{d} -all and the probe node m.victim._chk.<sender> exists:

Term under testOpenDMARCRspamdRequired
exists:%{p}._chk.%{d} (validated PTR)spf=pass — expands to m.victim, queries, matchesspf=fail — the term is droppedpass, or permerror if the letter is unsupported
exists:%{i}._chk.%{d} (same rig, swapped letter, control)passpasspass (consensus)

The control is what isolates the cause to the letter itself. The rig, the zone, the connecting address and the record shape are identical in both rows; only the macro letter changes, and only %{p} diverges.

Rspamd's own debug log states the mechanism and the omission in two consecutive lines:

expand_spf_macro: ... unknown or unsupported spf macro p ...
parse_spf_exists: unresolvable exists element

The second line is the defect. An unsupported letter is recognised as such and then treated as an unresolvable term rather than as the section 7.3 syntax error it is.

A fallback sweep, run with a validated %{p} that OpenDMARC matches, shows what the dropped term leaves behind. In every case Rspamd simply evaluates the remainder of the record:

Record after the exists:%{p} termRspamd resultRequired
-allfailpermerror
~allsoftfailpermerror
?allneutralpermerror
a later non-matching +ip4failpermerror

Under -all the outcome is merely wrong. Under ~all and ?all the outcome is wrong in the permissive direction, and a record whose remainder authorises the connecting host would be authorised outright on the strength of a term the verifier could not evaluate.

Proof of Concept

Publish, for a sender that uses validated-PTR SPF:

sender.example.             IN TXT "v=spf1 exists:%{p}._chk.%{d} -all"
m.victim._chk.sender.example. IN A   203.0.113.45
45.113.0.203.in-addr.arpa.  IN PTR "m.victim."
m.victim.                   IN A   203.0.113.45

Send from 203.0.113.45 with MAIL FROM:<alice@sender.example>. Required: %{p} validates to m.victim, the probe node exists, the exists term matches and the result is spf=pass; or, if the implementation does not support the letter, permerror per section 7.3. Observed on OpenDMARC: spf=pass. Observed on Rspamd: spf=fail, with the term dropped and -all applied.

Mitigation

Implement the p macro letter in the SPF macro expander: perform the PTR lookup for the client address and accept a name only when a forward lookup of that name contains the client address, per RFC 7208 sections 7.2 and 5.5, substituting unknown where no name validates.

Independently of that, and regardless of which letters are implemented, an unrecognised macro letter must abort the evaluation with permerror as section 7.3 requires, rather than making the containing term unresolvable. The second change is the smaller of the two and closes the fail-open shape on its own.

Notes

The same method, a DNS toggle against a single macro letter, produced a companion Rspamd finding on the %{dN} digit transformer (rspamd-macro-digit-transformer) and an OpenDMARC finding on %{l}. The two Rspamd macro-expansion gaps share a code path and should be disclosed together.

Swept and recorded as consensus, not as bugs: %{ir}, the reversed-dotted client address, expands identically on both verifiers, with the forward-order probe failing on both and the reversed-order probe passing on both; %{v} resolves to in-addr for IPv4 on both; the ptr: mechanism, as distinct from the %{p} macro, is correct on both including the forward-mismatch case; and the exp-only macros %{c}, %{r} and %{t} used inside a mechanism produce spf=fail on both, neither escalating to permerror, which is an industry consensus rather than a differential. OpenDMARC is IPv4-only in this laboratory, so a native IPv6 %{v} could not be exercised on that side.

Harness note. OpenDMARC's SPFSelfValidate evaluates against the real SMTP peer address, which in the container network is private, and Rspamd skips SPF entirely for a private connecting address. To make both evaluate the same public address the rig transiently enabled Postfix XCLIENT and injected XCLIENT ADDR=203.0.113.45, verified through the Received: header, and added a PTR branch to the laboratory authoritative server, verified on the wire with drill -x. Both laboratory changes were reverted after the run. A standing PTR branch would make %{p} a repeatable capability of the rig.
