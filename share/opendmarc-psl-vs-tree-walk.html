OpenDMARC implements RFC 7489 Public Suffix List discovery and therefore never sees an RFC 9989 tree-walk policy at an intermediate label (OpenDMARC ≤ 1.4.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDMARC
Affected version: OpenDMARC 1.4.2, built from the upstream tarball rel-opendmarc-1-4-2. The finding was originally isolated on the Debian package 1.4.2-1+deb12u1 and re-confirmed against pristine upstream. Earlier 1.4.x and 1.3.x releases are expected to share the behaviour.
Vulnerable component: DMARC policy discovery — the RFC 7489 section 6.6.3 organisational-domain lookup, in place of the RFC 9989 section 4.8 label-by-label tree walk
Vulnerability type: None (an RFC 7489 versus RFC 9989 divergence, not a defect)
Attack vector: Not an attack. The exposure is a deployment consequence: it arises when a domain owner publishes DMARC only at an intermediate label, in anticipation of RFC 9989 adoption.
CVSS v3.1: Not applicable
Status: Reproduced 34 of 34 cases in run 20260527T165112-db7f9513, against an RFC 9989 specification modeller as the reference oracle.

Impact. Published for completeness and not submitted as a vendor vulnerability: OpenDMARC is faithful to RFC 7489 section 6.6.3, so this is a conformance and migration hazard during the 7489-to-9989 transition rather than an implementation flaw.

Description

The hazard is asymmetric and depends on operator deployment choices. A domain owner who anticipates RFC 9989 adoption, publishes DMARC at an intermediate tree level, and removes the record at the top-level organisational domain will find that tree-walk verifiers reject spoofs correctly while OpenDMARC-based verifiers deliver the same spoofs under “no policy”.

The second-order effect is measurement error. An operator auditing DMARC coverage against a single verifier will draw incorrect conclusions about how their policy is being applied elsewhere, in whichever direction their chosen verifier errs.

This is interoperability decay during a specification migration rather than a verifier-side exploit. It nonetheless deserves recording, because the transition is under way and OpenDMARC remains broadly deployed.

This entry is published for completeness and is deliberately not submitted as a vendor vulnerability. OpenDMARC 1.4.2 implements RFC 7489 section 6.6.3 faithfully and correctly. The behaviour recorded here is visible only when it is measured against RFC 9989 section 4.8, which replaced the Public Suffix List organisational-domain lookup with a DNS tree walk. It is a conformance and migration hazard for the period in which both discovery models are deployed, not an implementation flaw, and the appropriate request to the project is migration tooling rather than a fix.

RFC 9989 section 4.8 has a verifier walk up the DNS tree from the Author Domain one label at a time, looking for a _dmarc record at each level, until a record is found, a label declared psd=y is reached, or a maximum number of lookups has been performed. RFC 7489 section 6.6.3 instead queries _dmarc.<author> and, on NXDOMAIN, jumps directly to the Public Suffix List derived organisational domain and queries exactly once more.

A DMARC record published at an intermediate label is therefore authoritative to a tree-walk verifier and invisible to OpenDMARC.

OpenDMARC visits two nodes and only two: the Author Domain, and the organisational domain derived from the Public Suffix List. For the Author Domain a.b.c.example.com the two discovery models visit different sets of nodes:

Node queriedRFC 9989 section 4.8 tree walkOpenDMARC (RFC 7489 section 6.6.3)
_dmarc.a.b.c.example.com (the Author Domain)queriedqueried
_dmarc.b.c.example.comqueriednot queried
_dmarc.c.example.comqueriednot queried
_dmarc.example.com (the organisational domain)queriedqueried

The depth-3 reproducer publishes the policy at an intermediate label and nothing at the organisational domain:

sender-x.example.com.                  IN SOA ns.lab.test. h.lab.test. 1 60 60 60 60
sender-x.example.com.                  IN MX  10 mx.sender-x.example.com.
sender-x.example.com.                  IN TXT "v=spf1 +all"
_dmarc.sender-x.example.com.           IN TXT "v=DMARC1; p=quarantine"
sub.sender-x.example.com.              IN SOA ns.lab.test. h.lab.test. 1 60 60 60 60
deep.sub.sender-x.example.com.         IN SOA ns.lab.test. h.lab.test. 1 60 60 60 60
default._domainkey.deep.sub.sender-x.example.com. IN TXT "v=DKIM1; k=rsa; p=..."

A DKIM-signed message with From: alice@deep.sub.sender-x.example.com then produces:

VerifierDiscovery pathVerdict
RFC 9989 specification modellerwalks up and finds the policy at _dmarc.sender-x.example.comdmarc=pass
OpenDMARC 1.4.2queries _dmarc.deep.sub.sender-x.example.com, then jumps to _dmarc.example.comdmarc=none

The intermediate node that carries the policy is never consulted, because it is neither the Author Domain nor the Public Suffix List organisational domain. Reproducibility in the laboratory was 34 of 34 cases across the Author Domain shapes exercised.

Proof of Concept

# zone: the policy sits at an intermediate label, and nowhere else
_dmarc.sender-x.example.com.  IN TXT "v=DMARC1; p=quarantine"
# no record at _dmarc.example.com and none at _dmarc.deep.sub.sender-x.example.com

# message
From: alice@deep.sub.sender-x.example.com

An RFC 9989 verifier walks deep.sub.sender-x.example.com, sub.sender-x.example.com, sender-x.example.com, finds p=quarantine there, and evaluates against it. OpenDMARC stamps dmarc=none. The same zone with the policy moved to _dmarc.example.com makes both agree, which confirms that the intermediate placement is the only variable.

Mitigation

The request to the project is migration tooling, not a defect fix. Add RFC 9989 section 4.8 tree-walk discovery, gated behind a configuration directive so that operators can select the discovery model their deployment requires, and document the migration footprint: which node set each mode consults, and what a domain owner should expect from receivers still running the RFC 7489 model.

Nothing in the current behaviour needs to be corrected for OpenDMARC to remain conformant to the specification version it implements.

Notes

Why this is not submitted as a vendor vulnerability. There is no defect to report. RFC 7489 section 6.6.3 prescribes exactly the two-node lookup that OpenDMARC performs, and OpenDMARC performs it correctly. The divergence exists because RFC 9989 replaced that lookup, and it will persist for as long as the two discovery models coexist in deployment. Assigning a vulnerability to a faithful implementation of the specification it declares would be incorrect, so the disclosure framing is a migration-tooling request through the same maintainer chain, not a CVE candidate.

The exposure is also conditional on a deployment choice that few domains have yet made. A domain that publishes at its organisational domain, as almost all currently do, is unaffected in both models.

Recorded as future laboratory work: a mode=7489 variant of the case generator, so that the same Author Domain shapes can be asserted against an explicit RFC 7489 verdict, which tests OpenDMARC against the specification it implements rather than against the one that replaced it.
