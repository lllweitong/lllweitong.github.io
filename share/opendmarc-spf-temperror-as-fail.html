OpenDMARC maps a transient DNS failure on the SPF record lookup to spf=fail instead of temperror, turning a brief DNS outage into permanent mail loss (OpenDMARC ≤ 1.4.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDMARC (SPFSelfValidate)
Source code: https://github.com/trusteddomainproject/OpenDMARC
Affected version: OpenDMARC 1.4.2, built from the upstream tarball rel-opendmarc-1-4-2. The finding was originally isolated on the Debian package 1.4.2-1+deb12u1 and re-confirmed against pristine upstream. Earlier 1.4.x and 1.3.x releases are expected to share the behaviour.
Vulnerable component: SPF evaluation in SPFSelfValidate — the DNS error path for the initial TXT fetch of the sender's SPF record
Vulnerability type: CWE-754 (Improper Check for Unusual or Exceptional Conditions)
Attack vector: Remote, and no attacker is required: any transient failure at the sending domain's authoritative name servers triggers it. An attacker able to disrupt those servers — a flood, a rate-limit trip, or a DNSSEC mis-signing they can provoke — can trigger it deliberately against a chosen sender.
CVSS v3.1: 5.9 (Medium) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:H
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Confirmed for SERVFAIL, REFUSED and timeout under DNS fault injection, with a served-record control and with OpenDMARC's own correct handling of a sub-lookup failure as the internal oracle.

Impact. A SERVFAIL, REFUSED or timeout on the sender's own v=spf1 lookup is reported as a permanent spf=fail, so under p=reject legitimate mail is rejected rather than deferred for retry.

Description

A denial of validation that fails closed. For a message authenticated by SPF alone, with no DKIM signature, spf=fail produces dmarc=fail, and under the sending domain's own p=reject the receiver rejects permanently. The sending domain therefore loses legitimate mail outright during any transient failure of its authoritative DNS, where the specified temperror would have caused a deferral and successful delivery on retry.

Transient SERVFAIL, REFUSED and timeout conditions are routine in operation: DNSSEC signing mistakes, rate-limited or overloaded authoritative servers, anycast route changes and brief network partitions all produce them, typically for minutes. On OpenDMARC receivers each such window converts into bounced mail rather than delayed mail, and the bounce is attributed to the sending domain's own published policy, which makes the cause hard to diagnose from either end.

The exposure is not attacker-driven in the usual sense, but it is attacker-reachable: anyone able to push a target's authoritative servers into SERVFAIL or rate-limiting for a short period can cause that target's mail to be rejected rather than queued during the window.

RFC 7208 section 2.6.7 defines temperror as the result to be returned when the evaluation could not be completed because of a transient condition, and section 4.4 places the initial fetch of the sender's SPF record squarely in that category: a DNS error other than “no record” is a transient failure and the receiver is expected to defer and retry.

OpenDMARC's SPFSelfValidate returns spf=fail for these instead. A failure to obtain the record is treated as though the record had been obtained and had evaluated to a no-match against -all. The result is permanent where the specification requires a temporary one, and the consequence is that a brief DNS blip at the sender becomes a hard rejection at every OpenDMARC receiver.

The served control matters: it shows that the rig reaches a genuine fail by the ordinary route, so the faulted rows are not simply the rig failing to evaluate at all.

OpenDMARC is self-inconsistent, and that is the strongest evidence here. The implementation does have a temporary-error path, and it uses it correctly — but only for lookups performed during evaluation, not for the fetch of the record itself. The same SERVFAIL, from the same resolver, in the same verifier, is mapped two different ways depending only on which lookup encountered it:

Because the in-evaluation path returns a temporary error as required, the defect cannot be explained as a deliberate design choice to avoid deferrals, nor as a missing capability. It is localised to the record-fetch error path, which conflates “the record could not be fetched” with “the record was fetched and did not authorise this client”.

Proof of Concept

Publish, for a sending domain, and configure the authoritative server so the fault can be toggled for the TXT lookup of sender.example alone:

sender.example.        IN TXT "v=spf1 ip4:203.0.113.9 -all"
_dmarc.sender.example. IN TXT "v=DMARC1; p=reject; aspf=r; adkim=s"

Send an unsigned message with From: billing@sender.example and MAIL FROM:<billing@sender.example>, first with the record served and then with the authoritative server answering SERVFAIL for that one name:

MAIL FROM:<billing@sender.example>
RCPT TO:<user@receiver.test>
DATA
From: billing@sender.example
To: user@receiver.test
Subject: monthly statement

...
.

Required under RFC 7208 sections 2.6.7 and 4.4 in the faulted case: spf=temperror, which propagates to a DMARC temporary error and a 4xx deferral, so the message is retried and delivered once DNS recovers. Observed on OpenDMARC: spf=fail, hence dmarc=fail, hence a permanent rejection under p=reject. Rspamd on the identical transaction returns R_SPF_DNSFAIL and defers.

Because the record cannot be fetched at all in the faulted case, the connecting address is not consulted, so a host the record does authorise receives the same spf=fail. That is the shape of the harm: mail that would have passed SPF a second earlier is rejected outright.

The self-inconsistency is reproduced with the same rig by serving sender.example. IN TXT "v=spf1 exists:exists.%{d} -all" successfully and faulting only exists.sender.example, which yields spf=tempfail.

Mitigation

In the record-fetch path, distinguish a DNS error from a successful lookup that returned no record. A SERVFAIL, REFUSED, timeout or other transient resolver failure must yield temperror, per RFC 7208 sections 2.6.7 and 4.4; only NXDOMAIN or a successful answer containing no v=spf1 record yields none, and only a completed evaluation yields fail.

The temporary-error path already exists and is already reached correctly from the in-evaluation lookups, so the change is to route the record-fetch error into it rather than into the no-match result.

Notes

The counterpart defect in the DMARC record lookup fails in the opposite direction: a transient failure there yields dmarc=none and lets forgeries through. Both share one root theme, which is that OpenDMARC has no proper temporary-error path for the record lookups themselves, and they are best fixed together.

No claim is made here that an attacker gains authentication they should not have. The direction is strictly fail-closed, and the entry is filed as a conformance and availability defect for that reason.
