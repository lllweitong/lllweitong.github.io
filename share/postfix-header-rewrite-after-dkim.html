Postfix rewrites an over-long header line after the milter chain has stamped dkim=pass, so the trusted verdict covers bytes the recipient never receives (OpenDKIM <= 2.11.0 and OpenDMARC <= 1.4.2 and Postfix ≤ 3.10.12)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Postfix project (Wietse Venema)
Software: Postfix, in a milter chain with OpenDKIM and OpenDMARC
Affected version: Postfix 3.10.12 in a milter chain with OpenDKIM 2.11.0 and OpenDMARC 1.4.2. The finding was originally isolated on Postfix 3.7.11. The defect is one of pipeline ordering rather than of any single component's own logic.
Vulnerable component: Milter pipeline ordering — the interaction between smtp_line_length_limit line rewriting and milter-time DKIM verification
Vulnerability type: CWE-367 (Time-of-check Time-of-use (TOCTOU) Race Condition)
Attack vector: Remote, unauthenticated, but with an abnormal precondition: the message must carry a single header line longer than 998 octets. Above approximately 2048 octets the milter rejects the message with 550, so the usable window is bounded.
CVSS v3.1: 4.0 (Medium) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:C/C:N/I:L/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Deterministic, with signed and unsigned controls, two other MTAs as differential peers, a short-message control, an upper-bound control, and a byte-level verification split computed outside the chain.

Impact. A header line longer than 998 octets is mutated after OpenDKIM verified it, leaving a trusted Authentication-Results: dkim=pass on a message whose signed header no longer verifies.

Description

Two effects, both narrow.

A DKIM end-to-end integrity break. DKIM exists so that a recipient can confirm that the header fields it covers arrived unaltered. Here a covered header field is altered inside the receiving infrastructure after verification, and the delivered message no longer matches the canonicalised header that was authenticated.

A stale trusted verdict. The Authentication-Results header bearing the receiver's own identifier says dkim=pass for a message whose signed header is now broken. Any downstream consumer that trusts that header without re-verifying — which is the ordinary reason the header exists — is acting on a verdict that no longer describes the message it holds.

The precondition is abnormal. Header lines over 998 octets do not occur in ordinary mail, and the milter rejects beyond roughly 2048 octets, so the window is both unusual and bounded. The severity above reflects that.

RFC 5321 section 4.5.3.1.6 sets the 998-octet text line limit that triggers this. Postfix inserts a single bare space (0x20) at octet 998 of any header line longer than that, under smtp_line_length_limit=998. The insertion is a space on one physical line, not an RFC 5322 CRLF-plus-whitespace fold, and the line remains over the limit afterwards — 1129 octets in the case measured.

OpenDKIM verifies the message and stamps Authentication-Results: receiver.test; dkim=pass before that insertion happens. The delivered message carries the post-insertion header. The trusted verdict therefore describes bytes the recipient never receives, and the signature over the bytes that are delivered does not verify.

The proof that OpenDKIM verified the pre-insertion bytes is byte-level and does not depend on re-verifying anything downstream. For a d=victim, c=simple/simple, aligned signed message, the identical signature verifies over the un-spaced From header and fails over the octet-998-spaced one:

Header bytes the signature is checked againstVerification result
the From as signed, no insertiontrue
the From as delivered, one space inserted at octet 998false

Since OpenDKIM reported dkim=pass and the signer signed the un-spaced bytes, OpenDKIM necessarily verified the pre-insertion form. The same holds for relaxed canonicalisation, because a space injected between two non-whitespace characters survives whitespace collapsing rather than being folded away.

Controls, all deterministic, separate the Postfix behaviour from the milter behaviour and bound the window:

ControlObservationWhat it establishes
the same over-long header on an unsigned messagespace still inserted at octet 998the mutation is Postfix's, not OpenDKIM's
the same over-long header through OpenSMTPD, no miltersdelivered verbatim at 1128 octets, no insertionthe rewrite is specific to this MTA, not inherent to the transport
the same over-long header through Eximrejecteda third behaviour: refusing the input outright
a short signed messageno insertion, dkim=pass holds end to endthe rig is otherwise sane
a header line beyond approximately 2048 octets550 milter rejectthe precondition window is bounded above, and that end fails closed

Octet 998 can be steered into different parts of the From value by padding the display name or the local part, so the inserted space can be made to land in the display name, in the local part, or inside a domain label. In the last case the delivered header reads vic60 46c7.com while the Authentication-Results header.from and header.d still name the intact vic6046c7.com with dkim=pass.

Proof of Concept

Sign a message with c=simple/simple for a domain that publishes an aligned policy, and pad the From header so that the line exceeds 998 octets with octet 998 falling inside the domain label:

From: "AAAA...A (padding to place octet 998 inside the domain)" <ceo@vic6046c7.com>
DKIM-Signature: v=1; a=rsa-sha256; c=simple/simple; d=vic6046c7.com; s=sel;
    h=from:to:subject; bh=...; b=...

Submit it through the Postfix plus OpenDKIM plus OpenDMARC chain. Required: either the message is rejected, or the header is folded conformantly and the verdict describes the delivered bytes. Observed:

# header stamped by the chain
Authentication-Results: receiver.test; dkim=pass header.d=vic6046c7.com
    header.from=vic6046c7.com

# the From line actually delivered
From: "AAAA...A" <ceo@vic60 46c7.com>
                            ^ one space inserted at octet 998

Checking the delivered From against the same signature outside the chain returns false, while checking the un-spaced form returns true. The trusted dkim=pass therefore rides on bytes the recipient never receives.

Mitigation

Bound or fold over-long header lines before the milters run, or re-verify after any post-milter rewriting, so that the bytes verified are the bytes delivered. Either ordering closes the gap; the present ordering does not.

Independently, the rewrite itself is worth revisiting: inserting a bare space at octet 998 does not produce a conformant RFC 5322 fold and does not even bring the line under the limit, since the line remains over 998 octets afterwards. A CRLF-plus-whitespace fold, or a rejection, would both be more defensible than a mutation that changes the meaning of the field while leaving it just as long.

Notes

This is not a spoof. The attacker cannot choose what is inserted — it is always a single space, and always at octet 998 — so a victim domain can only be corrupted, never substituted for an attacker's domain. The authenticated mailbox and the delivered mailbox remain the same modulo the corrupting space. The value to an attacker is limited to the integrity break and to downstream consumers that trust the receiver's Authentication-Results without re-verifying.

Scope of the RFC claim. The defensible statement is that the delivered message no longer matches the canonicalised header OpenDKIM authenticated, while the receiver still emits dkim=pass. RFC 6376 section 3.4.1 is cited for the canonicalisation the signature is taken over and RFC 5321 section 4.5.3.1.6 for the 998-octet trigger. It is deliberately not claimed that Postfix violates the canonicalisation rules: the byte mutation originates in Postfix, but the primary defect is that the receiving pipeline permits post-authentication mutation of DKIM-covered header bytes while preserving the verdict written beforehand.

Methodology caveat. Re-verifying the delivered copy retrieved from the laboratory sink is not a valid oracle and was not used as one. That copy is contaminated: the relay reorders header fields and prepends Return-Path, DMARC-Filter and Received, so even short control messages fail a naive verification of the sink copy. The evidence used here is OpenDKIM's own Authentication-Results, the byte-level verification split computed outside the chain, and the controls above.

Distinct from the inbound forged-Authentication-Results finding in this series, which runs in the opposite direction: there an attacker injects a header from outside, whereas here the chain's own legitimately stamped verdict goes stale because the message is mutated after the milter signed off.
