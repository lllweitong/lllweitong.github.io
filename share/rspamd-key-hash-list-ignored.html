Rspamd ignores the DKIM key record's h= hash-algorithm restriction, so a key verifies signatures made with a hash the key owner excluded (Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Rspamd project (Vsevolod Stakhov)
Software: Rspamd
Source code: https://github.com/rspamd/rspamd
Affected version: Rspamd 4.1.2. Originally isolated on 3.10.2 and re-confirmed on 4.1.2 on 2026-07-28. OpenDKIM 2.11.0 enforces the restriction correctly.
Vulnerable component: DKIM public-key record handling — the h= acceptable-hash list of RFC 6376 section 3.6.1, which section 6.1.2 requires the verifier to check
Vulnerability type: CWE-347 (Improper Verification of Cryptographic Signature) / CWE-757 (Selection of Less-Secure Algorithm During Negotiation)
Attack vector: Remote. The victim key record must publish h=, and the attacker must present a signature whose hash algorithm that list excludes.
CVSS v3.1: 3.7 (Low) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Isolated from a DKIM key-record differential sweep and re-confirmed with a direct OpenDKIM-versus-Rspamd probe in which only the h= tag varies.

Impact. A key record that permits only one hash still verifies a signature made with another, so the h= downgrade restriction is unenforced on Rspamd.

Description

The h= tag is a per-key algorithm policy, and its practical purpose is downgrade protection. A domain that provisions a key for SHA-256 use only publishes h=sha256 so that the key can never be honoured for a weaker rsa-sha1 signature, which RFC 8301 deprecates but which legacy verifiers still accept. On Rspamd that protection does not exist: the restriction is published, is visible in DNS, and is never consulted.

The consequence is bounded and should be stated plainly. The party that publishes h= is the party that owns the key, so this is not by itself a route to forging a victim's signature. It removes a receiver-side defence the key owner has explicitly asked for, so an adversary who can produce a signature under an excluded and weaker algorithm — the case h= exists to prevent — is accepted by Rspamd where a conforming verifier refuses the key outright. Operators cannot rely on h= for algorithm agility or for staging a hash migration on any receiver running Rspamd.

RFC 6376 section 3.6.1 defines the key record's h= tag as the colon-separated list of hash algorithms the key may be used with. Section 6.1.2 step 1 makes the check a MUST: “If the h= tag exists in the public-key record, the hash algorithm implied by the a= tag in the DKIM-Signature header field MUST be included in the contents of the h= tag; if not, the verifier MUST ignore the key record”, which makes the signature fail.

Rspamd never performs the comparison. Its DKIM verdict is invariant to the content of h=: a key record restricted to one hash still yields R_DKIM_ALLOW for a signature made with a different one. OpenDKIM enforces the restriction and reports dkim=fail with the reason signature-key hash mismatch.

The probe holds the message, the key and the signature fixed — one valid rsa-sha256 signature throughout — and varies only the h= tag of the key record:

The first two rows are what make the finding a genuine under-enforcement rather than a blanket “Rspamd always passes”. Rspamd accepts the legitimately permitted combinations as well, so the verdict is not a constant; it simply never rejects the one combination the specification requires it to reject. The no-h= control establishes the baseline against which the restricted record is compared, and it is identical, which is the direct statement that the tag has no effect on the verdict.

The tested direction is a key restricted to SHA-1 presented with a SHA-256 signature, because that combination can be produced from a single valid signature without weakening the signature itself. The security-relevant direction is the mirror image, a key restricted to h=sha256 presented with an rsa-sha1 signature, and it follows from the same invariance: the verifier does not read the tag in either direction.

Proof of Concept

Publish a key record that restricts the key to SHA-1, and sign with SHA-256:

sel._domainkey.signer.example.  IN TXT "v=DKIM1; k=rsa; h=sha1; p=<base64 RSA public key>"

Sign the message with the matching private key, using the signature tags:

DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=signer.example; s=sel;
    h=from:to:subject:date; bh=<body hash>; b=<signature>

Required under RFC 6376 section 6.1.2 step 1: the hash implied by a=rsa-sha256 is not in the record's h=sha1 list, so the verifier must ignore the key record and the signature must fail. Observed on Rspamd: R_DKIM_ALLOW. Observed on OpenDKIM with the identical message and record: dkim=fail with reason="signature-key hash mismatch".

Swap h=sha1 for h=sha256 or h=sha1:sha256 and both verifiers pass, which confirms that the rig is exercising the tag and not a broken record.

Mitigation

When the key record carries an h= tag, compare the hash algorithm implied by the signature's a= tag against the list before using the key, and treat the key record as unusable when the algorithm is absent, per RFC 6376 section 6.1.2 step 1. An empty or unparseable h= list should likewise make the record unusable rather than be silently skipped.

Notes

Deployment of the h= key tag is uncommon, which bounds how often the missing check is reachable in the field. That is a statement about exposure, not about correctness: the clause is a MUST, and Rspamd is the outlier against OpenDKIM.

The divergence is established behaviourally. The point in Rspamd's DKIM verifier at which h= is parsed but not enforced has not been identified in source, and confirmation against upstream rspamd_dkim remains an open step, so this report describes observed behaviour rather than a specific code path.

Part of the Rspamd DKIM constraint cluster together with rspamd-auid-subtree-unchecked (the i= AUID subtree check) and rspamd-key-service-tag-ignored (the s= service type). All three are the same shape: a constraint the specification requires the verifier to check is parsed or skipped but never applied.
