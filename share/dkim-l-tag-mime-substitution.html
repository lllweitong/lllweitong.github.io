A signer that omits Content-Type from h= while using l= permits MIME-boundary substitution, so a dkim=pass message renders content the signer never authored (OpenDKIM ≤ 2.11.0)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Not applicable - the DKIM verifier is specification-correct; the fix belongs with each signer
Software: OpenDKIM (verifier under test)
Affected version: OpenDKIM 2.11.0 (Debian package 2.11.0~beta2-9.1+b1). The verifier behaviour is not version-specific: any conforming DKIM verifier returns the same result on this input. The header-duplication mapping in the notes was made against Postfix 3.7.11.
Vulnerable component: DKIM signer policy — h= header-field selection combined with the l= body-length limit. The verifier path is not implicated.
Vulnerability type: CWE-345 (Insufficient Verification of Data Authenticity) at the composed-system level; no verifier defect
Attack vector: Remote. The attacker must be able to modify the message after signing, which means any hop on the delivery path, any mailing list or forwarder, or simply resending a copy of a signed message obtained from the signer.
CVSS v3.1: Not applicable
Status: Reproduced 3 of 3 through fuzz/generators/mime_boundary_cases.py, end to end from signer to delivered message, with the Content-Transfer-Encoding variant of the same shape confirmed 3 of 3 alongside it.

Impact. Published for completeness and not submitted as a vendor vulnerability: the DKIM verifier is specification-correct and the weakness is a signer-side policy choice that RFC 6376 section 8.2 documents explicitly.

Description

A deliverable message that carries dkim=pass, an aligned d= and therefore dmarc=pass, while the content a recipient actually sees was authored by the attacker. Receivers and downstream consumers, including brand-indicator rendering and reputation systems, treat dkim=pass as evidence that the rendered message is authentic, and that inference is what breaks.

The per-signer severity is high where the signer is a brand whose From domain is attractive to phishers. The verifier-side severity is nil, because the verifier behaved as specified.

The primitive generalises. Postfix 3.7.11 rejects duplicate From, Reply-To, To, Cc, Subject, Date, Message-ID, In-Reply-To and References headers, but accepts duplicate Content-Type, Content-Transfer-Encoding, MIME-Version and the entire X- namespace. Every header in the accepted-by-transport and read-by-client intersection carries the same shape. A Content-Transfer-Encoding variant, in which the attacker prepends base64 above a signed 7bit and chooses body bytes that are valid base64, reproduces identically, 3 of 3.

This entry is published for completeness and is deliberately not submitted as a vendor vulnerability. The DKIM verifier is specification-correct: no RFC clause requires Content-Type to appear in h=, so a verifier confronted with this message is right to report dkim=pass. The weakness is a signer-side policy choice, and RFC 6376 section 8.2 already documents the surface it opens. There is no vendor defect to assign, and the fix belongs with each signer.

A signer that omits Content-Type from the h= tag while using l=, historically common at large producers, lets any later hop prepend a second Content-Type header carrying a different boundary= parameter and append a MIME part that references the new boundary after the signed body cut. The signed bytes still hash correctly, so the verifier reports dkim=pass; the receiving mail client renders the attacker's MIME tree, because the topmost Content-Type declares the new boundary.

The result is a deliverable message that is fully authenticated under DKIM and DMARC and whose visible rendering contains content the signer never produced.

The laboratory signer simulates a vulnerable producer. It signs with h=from:to:subject:date:message-id:mime-version, which omits content-type, and with l=145, the length of the canonicalised body, using a fresh 1024-bit RSA key published at a per-run selector. XXXX below stands for the random suffix the laboratory generates for each run, so that no two runs share a domain or a cached DNS answer:

To: Bob <bob@receiver.example.com>

The post-signing mutation is two edits: one header prepended above the signed block, and one MIME part appended past the l= cut.

Content-Type: multipart/mixed; boundary="ZZZ_attacker_boundary"

--ZZZ_attacker_boundary
Content-Type: text/plain; charset=us-ascii

ATTACKER-CONTROLLED CONTENT - would render in MUA but was never signed.
--ZZZ_attacker_boundary--

The unprotected annotation in the OpenDKIM result is the verifier stating, correctly, that headers outside h= are not covered. It is informational and does not change the pass.

Proof of Concept

Against any signer whose h= omits content-type and whose signature carries an l= tag, take a signed message and apply two edits:

# 1. prepend, above every existing header
Content-Type: multipart/mixed; boundary="ZZZ_attacker_boundary"

# 2. append, after the final signed octet counted by l=
--ZZZ_attacker_boundary
Content-Type: text/plain; charset=us-ascii

ATTACKER-CONTROLLED CONTENT
--ZZZ_attacker_boundary--

Required and observed are the same thing here, which is the point of the entry: the verifier reports dkim=pass, and with d= equal to the From domain the message is also DMARC-aligned. The divergence is not between verifier and specification but between the signed bytes and the rendered tree.

Mitigation

Signer side, which is where the fix belongs. Include Content-Type and Content-Transfer-Encoding in h=; oversign them by naming each one more time than it occurs, so that an added instance invalidates the signature; and avoid l= unless a specific deployment requires it, since section 8.2 identifies it as the enabling half of this surface.

Verifier side, optional and additive rather than corrective. A verifier or filter may re-canonicalise the MIME tree and emit a warning where a signature passes but the outer Content-Type that would be rendered differs from the signed instance, reported as a distinct Authentication-Results token rather than as a DKIM failure.

Notes

Why this is not submitted as a vendor vulnerability. The verifier is correct. RFC 6376 section 3.5 leaves the choice of h= to the signer, section 5.4 advises the signer to choose carefully because header fields not protected by the signature can be modified in transit, and section 8.2 explicitly names l= together with unsigned headers as a third-party body insertion surface. A verifier that reported anything other than pass here would itself be non-conformant. There is accordingly no vendor defect to assign, and the mitigation is a policy change at each signer.

The primitive is not new. It reproduces the case publicly disclosed by Zone.eu in May 2024 against a number of large brands. The contribution recorded here is a reproducible artefact against a current verifier and a generator that can probe any signer's h= policy at scale, not a novel weakness.

The boundary at which this would become a submittable finding is stated for the record: if a verifier were observed to diverge from the specification-conformant behaviour on these inputs, that verifier's behaviour would be a separate and reportable finding. None was observed.
