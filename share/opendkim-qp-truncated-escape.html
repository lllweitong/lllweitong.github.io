OpenDKIM input-buffer over-read in dkim_qp_decode() on a truncated quoted-printable escape (OpenDKIM ≤ 2.11.0)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDKIM (libopendkim)
Source code: https://github.com/trusteddomainproject/OpenDKIM
Affected version: OpenDKIM 2.11.0 (2.11.0~beta2-9.1+b1) and current upstream master.
Vulnerable component: libopendkim/util.c, dkim_qp_decode() line 344; reached from dkim_sig_domainok() at dkim.c:1602
Vulnerability type: CWE-125 (Out-of-bounds Read)
Attack vector: Remote, unauthenticated. One inbound e-mail carrying a DKIM-Signature header with an i= tag.
CVSS v3.1: 8.2 (High) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:H
Status: AddressSanitizer-confirmed against a library already patched for the two earlier libopendkim defects, the output-side off-by-one in the same function and the h= tag write.

Impact. An i= tag ending in a bare '=' makes the decoder skip past the NUL terminator and read beyond the end of the input buffer.

Description

An out-of-bounds read of the heap buffer holding the DKIM-Signature tag value, on every inbound signed message whose i= tag ends in a truncated escape. Under a sanitizer or a hardened allocator the verifier crashes, denying mail processing; on an ordinary build the decoder consumes adjacent heap bytes into the decoded AUID, which is then compared against the signing domain.

The quoted-printable decoder advances its input pointer by two after recognising a hexadecimal escape. When the input ends in a truncated escape — a trailing =, or = followed by a single hex digit — the escape is still recognised, because strchr(hexdigits, next) matches the NUL terminator itself, and p += 2 then steps past the end of the string. The next loop iteration dereferences *p beyond the allocation.

for (p = in, q = out; *p != '\0'; p++)        /* util.c:344 - *p reads out of bounds */
{
        switch (*p)
        {
          case '=':
                next1 = *(p + 1);
                if (next1 != '\0') next2 = *(p + 2);
                ...
                pos = strchr(hexdigits, next1);   /* matches the NUL terminator */
                ...
                p += 2;                           /* overshoots the NUL */

The trap is that strchr() treats its terminating NUL as part of the searched string and returns a non-NULL pointer for a NUL needle. A truncated escape therefore takes the hexadecimal path, and the unconditional p += 2 moves the cursor past the end of the input.

This is a distinct defect from opendkim-qp-off-by-one in the same function. That one is an output-side off-by-one; this is an input-side over-run, and each needs its own fix. It was only reachable once the off-by-one and the h= tag write had been patched, because the earlier crashes masked it.

Proof of Concept

A DKIM-Signature whose i= value ends in a bare =, or in = followed by exactly one hexadecimal digit:

DKIM-Signature: v=1; a=rsa-sha256; d=example.com; s=s1;
 i=user@example.com:=001;
 h=from; bh=...; b=...
# libopendkim patched for the two earlier defects, rebuilt with -fsanitize=address
./fuzz_odkim_verify crashes_dkv2/d-crash-...
==ERROR== AddressSanitizer: heap-buffer-overflow READ of size 1
          ... dkim_qp_decode util.c:344 <- dkim_sig_domainok dkim.c:1602

Mitigation

       case '=':
            next1 = *(p + 1);
+           if (next1 == '\0') break;           /* truncated escape at end of input */
            if (next1 != '\0') next2 = *(p + 2);
            ...
            pos = strchr(hexdigits, next1);
            if (pos == NULL) return -1;
+           if (next2 == '\0') break;
            pos = strchr(hexdigits, next2);
            ...
            p += 2;

The root cause to guard against is strchr(hexdigits, '\0') matching the terminator. Reject a NUL as a hexadecimal digit explicitly, and never advance p past the terminator.

Notes

Found by re-running the verification fuzzer against a library already patched for opendkim-qp-off-by-one and opendkim-h-tag-oob-write, which is why it should be treated as an independent issue rather than an incomplete fix for the off-by-one.
