OpenDMARC and Rspamd vendor different Public Suffix List snapshots, so a forged subdomain receives opposite DMARC verdicts and whichever list is staler fails open (OpenDMARC <= 1.4.2 and Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project and the Rspamd project (Vsevolod Stakhov)
Software: OpenDMARC and Rspamd
Source code: https://github.com/trusteddomainproject/OpenDMARC
Affected version: OpenDMARC 1.4.2, built from the upstream tarball rel-opendmarc-1-4-2. The finding was originally isolated on the Debian package 1.4.2-1+deb12u1 and re-confirmed against pristine upstream. Earlier 1.4.x and 1.3.x releases are expected to share the behaviour. Rspamd 4.1.2. Originally isolated on 3.10.2 and re-confirmed on 4.1.2 on 2026-07-28. Both are affected, symmetrically: for any given suffix the exposed side is whichever project vendored the staler list.
Vulnerable component: DMARC organisational-domain computation from each project's vendored Public Suffix List snapshot — /usr/share/publicsuffix/public_suffix_list.dat for OpenDMARC and /usr/share/rspamd/effective_tld_names.dat for Rspamd
Vulnerability type: CWE-346 (Origin Validation Error), arising from list data drift rather than from an algorithm defect
Attack vector: Remote, unauthenticated. One forged, unaligned message, provided the victim's registrable domain sits under a suffix on which the two snapshots disagree.
CVSS v3.1: 5.9 (Medium) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:H/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Confirmed in both directions, with the canonical publicsuffixlist library run over each container's own file reproducing every live verdict exactly.

Impact. Published for completeness and not submitted as a vendor vulnerability: the behaviour is real and exploitable, but the root cause is Public Suffix List data drift between the two vendored snapshots rather than an algorithm defect in either implementation.

Description

A registrant's p=reject is silently unenforced on whichever receiver vendored the staler list, for any registrable domain under a disagreed suffix. The disagreed set is large: it includes amplifyapp.com, the regional elasticbeanstalk.com forms, alpha.bounty-full.com and several hundred more entries in each direction.

The exposure is symmetric and persistent. The list changes roughly weekly and the two projects re-vendor it on different cadences, so a window of disagreement always exists; only its contents change. An attacker targeting a particular receiver selects a suffix on which that receiver's snapshot is the staler one.

What limits the assessment is that the victim's domain must happen to sit under a disagreed suffix, which the attacker cannot arrange. That precondition is what the attack-complexity metric records.

This entry is published for completeness and is deliberately not submitted as a vendor vulnerability. The fail-open is real and exploitable, but neither implementation is wrong. Each computes the organisational domain correctly from the Public Suffix List file it ships, and the two files differ. There is no single code fix to request and no defect to attribute to either project; the disclosure angle is list synchronisation.

The two verifiers vendor different snapshots of the list: OpenDMARC reads /usr/share/publicsuffix/public_suffix_list.dat, approximately 14,238 lines, and Rspamd reads /usr/share/rspamd/effective_tld_names.dat, approximately 16,179 lines. They differ by several hundred entries in each direction, mostly in the private section of the list where cloud providers register their suffixes.

For a From domain under a suffix on which the two files disagree, the verifiers compute different organisational domains, query different _dmarc nodes and reach opposite verdicts. Either side can be the one that fails open, depending on which snapshot lacks the entry.

The attack shape is a forged deeper label. The victim publishes p=reject; sp=reject at _dmarc.<org>, and the attacker forges From: ceo@sub.<org>. Because _dmarc.<From> is NXDOMAIN, each verifier falls back to its own computed organisational domain, and the two fall back to different nodes. With SPF -all and no DKIM signature:

Forged From domainOpenDMARCRspamd
sub.victim.amplifyapp.comorg amplifyapp.com → dmarc=none — fail-openorg victim.amplifyapp.com → DMARC_POLICY_REJECT
sub.app.af-south-1.elasticbeanstalk.comorg af-south-1.elasticbeanstalk.com → none — fail-openreject
sub.v.alpha.bounty-full.com (the flip)org v.alpha.bounty-full.com → dmarc=fail, disposition rejectorg bounty-full.com → DMARC_NA — fail-open

The third row is the one that establishes symmetry. Neither verifier is systematically the permissive one; the exposed side is whichever project's snapshot lacks the relevant entry, and an attacker chooses the suffix accordingly.

Four controls hold throughout. A message with From: ceo@<org> directly makes both verifiers find the policy through the From-domain query and both enforce, which shows the policy is published and reachable. A baseline forged subdomain under .com, a suffix both files agree on, makes both compute the same organisational domain and both reject, which shows that the combination of a forged subdomain and sp= is not itself the cause. A variant with p= only and no sp= keeps the split, so it is not an artefact of subdomain-policy handling. Finally, the canonical publicsuffixlist library, run over each container's own file, reproduces every live verdict exactly.

That last control is what removes the algorithm from suspicion. Each verifier agrees with a reference implementation reading the same file it reads. Both are self-consistent; the disagreement lives entirely in the data.

Proof of Concept

# zone: the victim's policy, at its organisational domain
_dmarc.victim.amplifyapp.com.  IN TXT "v=DMARC1; p=reject; sp=reject"
# nothing at _dmarc.sub.victim.amplifyapp.com and nothing at _dmarc.amplifyapp.com

# forged message: SPF -all, no DKIM signature
MAIL FROM:<bounce@attacker.invalid>
From: ceo@sub.victim.amplifyapp.com

Required: the organisational domain is victim.amplifyapp.com, the policy is found, alignment fails and the disposition is reject. Observed on Rspamd: DMARC_POLICY_REJECT. Observed on OpenDMARC: organisational domain amplifyapp.com, no policy found, dmarc=none, message delivered.

To reproduce the opposite direction, substitute a suffix present in OpenDMARC's file and absent from Rspamd's, such as the alpha.bounty-full.com case above, and the fail-open moves to Rspamd.

Mitigation

There is no single code fix, which is the substance of this entry. The practical remedies are operational. Both projects should document the freshness expectation for the list they vendor, and publish or pin a synchronised snapshot so that receivers can reason about which entries they hold. Packagers should prefer a single system-wide list over per-project copies where the platform provides one, and operators should be able to see which snapshot each verifier loaded.

Any residual algorithm-level improvement belongs to the entries that isolated one, not to this entry.

Notes

Why this is not submitted as a vendor vulnerability. Neither implementation departs from the specification or from its own data. The canonical publicsuffixlist run over each container's own file reproduces every live verdict exactly, so each verifier is provably self-consistent with the list it ships. Reporting this to either project as a defect would ask them to fix code that is correct. What the finding demonstrates is that the gap is exploitable for as long as the snapshots differ, which is perpetually, and that is a synchronisation and packaging matter.

Contrast with the two algorithm findings. opendmarc-psl-wildcard-orgdomain and rspamd-psl-rules-ignored are the complementary axis. Both deliberately held the Public Suffix List byte-identical between the two files and verified that the matched rule was identical in each, which left an algorithm defect as the only remaining explanation: the first pins OpenDMARC over-broadening the organisational domain under a wildcard rule, and the second pins Rspamd ignoring the * and ! constructs entirely. Those two are code defects and are put forward as such. This entry is the opposite case, where the algorithms agree and the data does not, and the two should not be read as variants of one another.

Two adjacent results are recorded so they are not mistaken for part of this finding. When _dmarc is actually published at a public suffix, both verifiers query and apply it, so both deviate from RFC 7489 section 3.2 in the same direction and there is no split; the lone asymmetry there is a bare From: admin@com with no _dmarc.com, which gives OpenDMARC none and Rspamd DMARC_DNSFAIL, a laboratory DNS response-code quirk for the SOA-less com node that leans temporary-error rather than fail-open. Separately, the _dmarc CNAME loop question is a harness gap and is neither confirmed nor refuted: the laboratory authoritative server collapses a loop into NODATA rather than returning the SERVFAIL a real recursive resolver would, so both verifiers see no policy and agree. That case needs a recursive resolver in the query path.
