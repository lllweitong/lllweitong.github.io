OpenDMARC and Rspamd repair a two-mailbox From header to opposite mailboxes, allowing a verifier-aware DMARC bypass (OpenDMARC <= 1.4.2 and Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project and the Rspamd project (Vsevolod Stakhov)
Software: OpenDMARC and Rspamd (both affected, in opposite directions)
Affected version: OpenDMARC 1.4.2 (takes the last mailbox) and Rspamd 4.1.2, originally isolated on 3.10.2 (takes the first).
Vulnerable component: DMARC Author Domain extraction from a malformed RFC 5322 From header
Vulnerability type: CWE-436 (Interpretation Conflict) leading to CWE-290 (Authentication Bypass by Spoofing)
Attack vector: Remote. The attacker needs a domain of their own with a valid DKIM key, which is freely obtainable.
CVSS v3.1: 7.5 (High) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Four of four deterministic, with separator, direction and single-domain controls.

Impact. From: ceo@victim.com ceo@attacker.com is silently repaired to the last mailbox by OpenDMARC and the first by Rspamd, so ordering picks which verifier is defeated.

Description

An attacker who can pass DKIM for their own throwaway domain constructs a From header containing both the victim and the attacker mailbox, ordered so that the target's verifier selects the attacker's aligned domain. The message obtains dmarc=pass while its From header still contains victim.com.

The attack is verifier-aware and covers the field: attacker-last defeats OpenDMARC, attacker-first defeats Rspamd. Since both implementations are wrong in opposite directions, one ordering or the other works against any given receiver.

How a mail client renders such a header determines the phishing value and was not measured here. The laboratory-confirmed part is the deterministic cross-verifier disagreement on Author Domain selection, on a message whose From visibly contains the victim's domain.

A From header containing two address specifications separated by a single space — From: ceo@victim.com ceo@attacker.com — is malformed. RFC 5322 section 3.6.2 requires comma separation and an accompanying Sender: for multiple mailboxes, and RFC 7489 section 6.6.1 says a message without exactly one parseable From mailbox should be treated as a DMARC failure.

Both verifiers instead silently repair the header to a single mailbox, and they pick opposite ones. OpenDMARC takes the last address specification; Rspamd takes the first. The attacker chooses the ordering to place their own aligned domain wherever the target's verifier looks.

The attacker controls attacker.com, holds a valid DKIM key for it, and signs d=attacker.com. The policy under test is p=reject; adkim=s:

From:OpenDMARCRspamdWho picked what
ceo@attacker.com (control)dmarc=passpassboth take the attacker, aligned
ceo@victim.com (control)dmarc=failfailboth take the victim, unaligned
ceo@victim.com ceo@attacker.comdmarc=pass (header.from=attacker)dmarc=fail (victim)OpenDMARC last, Rspamd first
ceo@attacker.com ceo@victim.comdmarc=fail (victim)dmarc=pass (attacker)OpenDMARC last, Rspamd first
ceo@victim.com, ceo@attacker.com (comma)no verdictnone / DMARC_NAboth reject — consensus

The controls isolate the mechanism completely. The comma form — the only RFC-valid mailbox list — makes both verifiers refuse, so the space separator is the trigger. A bare CR and a folded CRLF plus space behave like the space. A concatenated single token makes both pick the same domain. Reversing the order flips both verdicts, which demonstrates the selection rule rather than a domain-specific effect.

Critically, the DKIM signature is reported pass header.d=attacker.com by both verifiers on the identical message. The verdict split therefore arises purely from Author Domain selection, not from any difference in signature verification.

A NUL separator produces the same opposite-mailbox split by a different route: OpenDMARC truncates at the NUL and Rspamd reads past it.

Proof of Concept

# attacker's own domain, with a valid key and a reject policy
_dmarc.attacker.com.               IN TXT "v=DMARC1; p=reject; adkim=s"
sel._domainkey.attacker.com.       IN TXT "v=DKIM1; k=rsa; p=..."

# victim
_dmarc.victim.com.                 IN TXT "v=DMARC1; p=reject; adkim=s"

Send a message signed d=attacker.com with the attacker's own valid key and the header:

From: ceo@victim.com ceo@attacker.com

Required under RFC 7489 section 6.6.1: DMARC failure, because the header has no single parseable mailbox. Observed on OpenDMARC: dmarc=pass with header.from=attacker.com. Reverse the two mailboxes to obtain the same result on Rspamd.

Mitigation

Both implementations should follow RFC 7489 section 6.6.1 and treat a From header without exactly one parseable mailbox as a DMARC failure, rather than repairing it. Repairing a malformed header to any single mailbox is unsafe when implementations disagree about which one; the disagreement is the vulnerability.

Notes

Both projects are affected and both should receive the report. Neither implementation is “correct” here: the required behaviour is refusal, and first-wins and last-wins are both deviations.

Re-verified with distinct .com organisations and adkim=s, so organisational-domain and Public Suffix List computation cannot confound the result.
