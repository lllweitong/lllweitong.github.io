Rspamd and dkimpy do not enforce the DKIM key record's t=s strict flag, so a subdomain AUID is accepted against a key locked to its exact domain (Rspamd <= 4.1.2 and dkimpy ≤ 1.1.8)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Rspamd project (Vsevolod Stakhov) and the dkimpy maintainers (Scott Kitterman et al.)
Software: Rspamd and dkimpy
Source code: https://github.com/rspamd/rspamd
Affected version: Rspamd 4.1.2. Originally isolated on 3.10.2 and re-confirmed on 4.1.2 on 2026-07-28. dkimpy 1.1.8. OpenDKIM 2.11.0 enforces the flag correctly.
Vulnerable component: DKIM public-key record handling — the s (strict) value of the t= flags tag in RFC 6376 section 3.6.1
Vulnerability type: CWE-347 (Improper Verification of Cryptographic Signature) / CWE-20 (Improper Input Validation)
Attack vector: Remote. The victim key record must publish t=s, and the attacker must be able to produce a signature under that key carrying a subdomain AUID.
CVSS v3.1: 3.7 (Low) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Three deterministic repetitions with both isolating controls, and dkimpy cross-checked as a second non-enforcing implementation.

Impact. With t=s published, a signature carrying i=@sub.d must fail; Rspamd returns R_DKIM_ALLOW and dkimpy passes, while OpenDKIM alone enforces the flag.

Description

A domain sets t=s to lock a key to its exact domain, for instance to stop a delegated sub-signer, a departmental system or a tenant holding the key from claiming i=@sub.d as an authenticated identity. On Rspamd and dkimpy that lock has no effect, and the subdomain AUID is reported as authenticated.

The exposure is narrow and is described as such. The AUID is chosen by whoever signs, and t=s is rarely published, so few deployments are in a position to be affected. The finding's value is that it is a clean MUST violation shared by two independent implementations, and that it removes the only mechanism RFC 6376 provides for a key owner to forbid subdomain AUIDs on a key they have delegated.

RFC 6376 section 3.6.1 defines the s flag of the key record's t= tag: “Any DKIM-Signature header fields using the i= tag MUST have the same domain value on the right-hand side of the @ in the i= tag and the value of the d= tag. That is, the i= domain MUST NOT be a subdomain of d=.” The flag narrows the section 3.5 default, under which a subdomain AUID is perfectly legal, to exact equality.

Rspamd and dkimpy both ignore the flag. A signature carrying a subdomain AUID against a key published with t=s is accepted by both, where OpenDKIM correctly fails it. Here OpenDKIM is the lone enforcer and two implementations independently miss the same MUST.

The signature is valid throughout, and the i= tag is inside the signed tag set, so it is covered by b= and cannot have been added after signing. Only the key record's t= tag and the AUID form vary:

Key recordSignature i=OpenDKIMRspamddkimpyRequired
t=s@sub.d (subdomain)failR_DKIM_ALLOWpassfail
t=s:y (list form)@sub.dfailpasspassfail
(no t=, control)@sub.dpasspasspasspass
t=s (control)@d (exact)passpasspasspass

The two control rows isolate the flag completely. With t= absent, the subdomain AUID is legal and all three implementations correctly pass it. With t=s present but the AUID exactly equal to d=, all three correctly pass again. OpenDKIM's failure therefore arises only from the combination of the flag and the subdomain form, which is exactly the case section 3.6.1 converts from legal to invalid. Rspamd and dkimpy return the same verdict in all four rows, so neither reads the flag.

The t=s:y row shows that the omission is not a parsing artefact of the list form. Both non-enforcing implementations miss the flag whether it stands alone or appears alongside another flag.

Proof of Concept

Publish a key record with the strict flag set:

sel._domainkey.signer.example.  IN TXT "v=DKIM1; k=rsa; t=s; p=<base64 RSA public key>"

Sign the message with the matching private key, with the AUID set to a subdomain of the signing domain and included in the signed tag set so that it is covered by b=:

DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=signer.example; s=sel;
    i=user@sub.signer.example; h=from:to:subject:date; bh=<body hash>; b=<signature>

Required under RFC 6376 section 3.6.1: with t=s the AUID domain must equal d= and must not be a subdomain of it, so the signature is invalid. Observed on Rspamd: R_DKIM_ALLOW. Observed on dkimpy: verification returns true. Observed on OpenDKIM: failure.

Two controls complete the reproduction. Removing t=s from the record makes all three pass, which is correct under the section 3.5 default. Keeping t=s and setting i=user@signer.example also makes all three pass. The divergence appears only when both conditions hold at once.

Mitigation

Parse the key record's t= flags, including the list form, and when the s flag is present require the AUID domain to equal d= exactly rather than merely to lie within its subtree. Unknown flags in the list must continue to be ignored, per section 3.6.1, without that tolerance being extended to the flags that are recognised.

Notes

Distinct from rspamd-auid-subtree-unchecked, which is the section 3.5 default AUID constraint that a parent, sibling or unrelated AUID domain is invalid. This entry is the separate section 3.6.1 strict flag, which additionally forbids the subdomain form that the default constraint records as a correct pass. That baseline is exactly what t=s is supposed to flip.

An earlier laboratory run recorded t=s as a consensus with no divergence. That run exercised only the benign direction, t=s with an AUID equal to d=, and never the failing direction with a subdomain AUID, so the two results do not contradict one another. The earlier conclusion was incomplete rather than wrong.

Confirmation against upstream Rspamd and upstream dkimpy remains an open step, and the disclosure priority is correspondingly low: the flag is obscure, though the MUST is unambiguous.
