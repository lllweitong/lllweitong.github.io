OpenDMARC returns permerror for a malformed optional DMARC tag, silently disabling the record's p=reject (OpenDMARC ≤ 1.4.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDMARC
Source code: https://github.com/trusteddomainproject/OpenDMARC
Affected version: OpenDMARC 1.4.2, built from the upstream tarball rel-opendmarc-1-4-2. The finding was originally isolated on the Debian package 1.4.2-1+deb12u1 and re-confirmed against pristine upstream. Earlier 1.4.x and 1.3.x releases are expected to share the behaviour.
Vulnerable component: DMARC record parsing and tag validation
Vulnerability type: CWE-755 (Improper Handling of Exceptional Conditions)
Attack vector: Remote, unauthenticated. No attacker action against DNS is needed when the victim's record already carries a typo; otherwise the attacker must be able to influence the record.
CVSS v3.1: 7.5 (High) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. All 12 tested malformations diverged: OpenDMARC permerror against Rspamd pass.

Impact. A typo in a reporting-only tag such as fo=9 voids the whole policy, so spoofed mail in the domain's name passes.

Description

Any domain publishing p=reject with a minor typo in an optional tag is unprotected on every OpenDMARC receiver, while Rspamd, Gmail and other conforming verifiers still enforce the policy.

The failure is silent from the domain owner's side. Their own aligned mail continues to be delivered, now stamped permerror, and nothing is rejected, so there is no operational signal that protection has been lost. Malformed optional tags are common in published records (pct typos, fo/rf/ri mistakes, stray characters), which makes this a broad and quiet erosion of DMARC coverage rather than a corner case.

Where an attacker can influence the record — a hostile sub-delegate, a compromised registrar interface, a template that appends a tag — appending one malformed optional tag is a direct, deliberate way to disable the victim's policy.

RFC 7489 section 6.3 states that once v= and p= are valid, “syntax errors in the remainder of the record SHOULD be discarded ... or ignored outright”, and that unsupported report URIs MUST be ignored. Section 6.6.3 evaluates the p and sp policy.

OpenDMARC instead treats any tag with an invalid value as a fatal parse error and returns dmarc=permerror for the entire record. Since permerror is not fail, the reject policy is never applied. The protection is switched off by a typo in a tag that has no bearing on the authentication verdict at all.

With a valid v=DMARC1; p=reject prefix and one malformed optional tag appended, on an aligned DKIM-passing message:

Record (after v=DMARC1; p=reject;)OpenDMARCRspamdRequired
(no extra tag, baseline)passpasspass
fo=1, rf=afrf, ri=86400, pct=50, sp=none (all valid)passpasspass
fo=9 (invalid, reporting only)permerrorpasspass
rf=xml (invalid, reporting only)permerrorpasspass
ri=abc (invalid, reporting only)permerrorpasspass
pct=256 / pct=-1 (out of 0–100)permerrorpasspass
sp=foo, adkim=x, aspf=2 (invalid enumerations)permerrorpasspass
rua=mailto:a; rua=mailto:b (duplicate key)permerrorpasspass
fo=x, fo=0:1:9, rf=afrf:bogus (bad list member)permerrorpasspass
a single malformed rua= value (notauri, @@@, http://x, oversized list)passpasspass

The fo, rf and ri rows are the clearest cases: these are failure-reporting tags with no authentication semantics whatsoever, and one bad character in their value voids the entire p=reject.

OpenDMARC's report-address tolerance is per value, not per record. A single malformed rua= or ruf= value is accepted, but a duplicate rua= or ruf= key trips the permerror. Tag ordering makes no difference: a bad fo before or after p= behaves identically.

Proof of Concept

Publish, at a victim domain:

_dmarc.victim.example.  IN  TXT  "v=DMARC1; p=reject; fo=9"

Send a forged, unaligned message with From: ceo@victim.example, no DKIM signature, and an envelope sender in a different domain. Compare against the clean control record v=DMARC1; p=reject:

_dmarc.victim.exampleOpenDMARC verdict on the forgeryOutcome
v=DMARC1; p=rejectdmarc=failforgery caught
v=DMARC1; p=reject; fo=9dmarc=permerrorforgery delivered
v=DMARC1; p=reject; rf=xmldmarc=permerrorforgery delivered
v=DMARC1; p=reject; pct=256dmarc=permerrorforgery delivered

The delivered header carries no disposition, confirming that no policy was applied:

Authentication-Results: receiver.test; dmarc=permerror header.from=victim.example

Mitigation

Once v= and p= parse correctly, discard or ignore unparseable optional tags and continue to apply the policy, per section 6.3. Reserve permerror for records where the required tags themselves are absent or invalid. Unsupported report URIs must be ignored rather than treated as fatal, and a duplicate rua/ruf key should not be more fatal than a malformed value of the same tag.

Notes

Distinct from the multi-record and record-discovery findings: this is a single, correctly discovered record that parses to permerror purely because of an optional tag's value.

The root cause is over-strictness that becomes a fail-open one layer later: the parser fails closed to permerror, and permerror then fails open at the enforcement layer. See also opendmarc-subdomain-walk-abort (the same mishandling aborting the walk to the organisational domain) and dmarc-pct-integer-handling (the numeric edge cases of pct).
