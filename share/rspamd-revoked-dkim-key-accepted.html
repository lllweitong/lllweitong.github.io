Rspamd ignores DKIM key revocation when a valid p= tag coexists with the empty revocation marker (OpenDKIM <= 2.11.0 and Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Rspamd project (Vsevolod Stakhov)
Software: Rspamd (OpenDKIM is also non-conformant, in an order-dependent way)
Affected version: Rspamd 4.1.2, originally isolated on 3.10.2. OpenDKIM 2.11.0 is last-tag-wins; dkimpy is correct.
Vulnerable component: DKIM public-key record parsing — the p= field and the empty-value revocation marker
Vulnerability type: CWE-347 (Improper Verification of Cryptographic Signature) / CWE-299 (Improper Check for Certificate Revocation)
Attack vector: Remote. Requires the victim's key record to carry both values, through a stale entry, a mistaken revocation, or record injection.
CVSS v3.1: 5.9 (Medium) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:H/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Five repetitions with single-record controls in both directions.

Impact. A key record carrying both a valid p= and an empty p= still authenticates on Rspamd, in either tag order.

Description

A DKIM revocation bypass on Rspamd. A domain that has revoked a key but left a stale valid p= in the same record, or that fat-fingers the revocation, or whose record an attacker appends ; p=<old key> to, still authenticates signatures made with the revoked key. Because the test was configured with SPF -all and p=reject; adkim=s; aspf=s, the resulting dmarc=pass is reachable only through the revoked key, which pins the impact.

The trigger is a malformed duplicate-tag record, which bounds how often this arises naturally. The consequence when it does — a revoked key authenticating under p=reject — is a genuine authentication bypass.

RFC 6376 section 3.6.1 states that an empty p= means the key has been revoked, so a verifier must treat a signature made with it as failing. Section 3.2 states that duplicate tag names MUST NOT occur, so a record carrying two p= tags is malformed and should be rejected on that ground alone.

Rspamd takes the first parseable p= and never honours the empty revocation marker when a valid key coexists. It returns dkim=pass in both tag orders.

Key record at the selectorOpenDKIMRspamddkimpy
v=DKIM1; k=rsa; p=<valid>; p=dkim=fail, “key revoked” → dmarc=faildkim=pass → dmarc=passfail
v=DKIM1; k=rsa; p=; p=<valid>dkim=pass → dmarc=passdkim=pass → dmarc=passfail

OpenDKIM is last-tag-wins, so it happens to fail in one order and pass in the other. Rspamd is first-parseable-wins and passes in both. dkimpy rejects both, which is the correct handling of a duplicate-tag record.

The controls isolate the mechanism. A single valid record produces consensus dkim=pass; a single clean empty p= revocation produces consensus fail on all three, with OpenDKIM reporting “key revoked”, Rspamd R_DKIM_PERMFAIL and dkimpy a failure. Only the coexistence case diverges, so a clean revocation is honoured by every implementation and the defect is specific to the duplicate record.

Proof of Concept

sel._domainkey.victim.example.  IN TXT "v=DKIM1; k=rsa; p=<valid base64 key>; p="
_dmarc.victim.example.          IN TXT "v=DMARC1; p=reject; adkim=s; aspf=s"
victim.example.                 IN TXT "v=spf1 -all"

Send a message signed with the revoked key, from an unauthorised host so that SPF fails and DMARC can only pass through an aligned DKIM signature. Required: the key is revoked, DKIM fails, DMARC fails. Observed on Rspamd: dkim=pass and therefore dmarc=pass.

Mitigation

Reject a key record containing duplicate tag names, per section 3.2. Independently, honour an empty p= as a revocation even when a valid p= coexists, rather than taking whichever value happens to parse first. OpenDKIM's last-tag-wins behaviour is also non-conformant to section 3.2 and should be fixed in the same way.

Notes

A recorded negative result that bounds the claim: a clean single empty p= revocation, including the variants p= , tag-reordered, missing p=, and no v=, is honoured as revoked by all three implementations. The primary hypothesis — that revocation is broadly unhonoured — is a consensus with no bug. The divergence is specific to the coexistence case.
