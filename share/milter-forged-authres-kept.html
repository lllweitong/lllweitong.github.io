The OpenDKIM and OpenDMARC milter chain does not strip a forged Authentication-Results header bearing its own trusted authserv-id (OpenDKIM <= 2.11.0 and OpenDMARC ≤ 1.4.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDKIM and OpenDMARC, as a milter chain
Source code: https://github.com/trusteddomainproject/OpenDMARC
Affected version: OpenDKIM 2.11.0 and OpenDMARC 1.4.2, chained behind Postfix.
Vulnerable component: Authentication-Results handling — the RFC 8601 section 5 requirement to delete forged instances bearing the host's own authentication service identifier
Vulnerability type: CWE-290 (Authentication Bypass by Spoofing) / CWE-345 (Insufficient Verification of Data Authenticity)
Attack vector: Remote, unauthenticated. One inbound message with a prepended header.
CVSS v3.1: 5.8 (Medium) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:N/I:L/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Seven-variant survival table with foreign-identifier and baseline controls, using distinct .com organisations.

Impact. Six of seven forged Authentication-Results variants carrying the receiver's own trusted identifier survive into the delivered message.

Description

The impact is on downstream consumers, and this entry is scoped to that. Neither in-chain verifier's own verdict is affected: OpenDMARC reads the milter result rather than re-parsing inbound headers, and Rspamd recomputes, so both still report dmarc=fail.

The harm falls on anything that reads the delivered message and trusts the header: a Sieve rule or log parser that greps for Authentication-Results: receiver.test; ... dmarc=pass, a filter that trusts the first dmarc=pass from a trusted identifier, or a consumer that reads the Authentication-Results header nearest the From. The milter's genuine lines are prepended at the top, so the forged survivor sits lower, just above From — exactly where a bottom-up reader looks. This is precisely the attack section 5 exists to prevent.

RFC 8601 section 5 is a MUST: “any MTA conforming to this specification MUST delete any discovered instance of this header field that claims, by virtue of its authentication service identifier, to have been added within its trust boundary but that did not come directly from another trusted MTA.”

The chain does this only partially. OpenDKIM removes a pre-existing Authentication-Results header bearing the trusted identifier only when it carries a dkim= token; OpenDMARC removes nothing. A forged header bearing the trusted identifier but omitting dkim= therefore survives the whole chain and is delivered.

A forged, genuinely failing message — From=victim.com under p=reject; adkim=s; aspf=s, no aligned DKIM, envelope in attacker.net — with a forged Authentication-Results header prepended as the first header. The trusted identifier is receiver.test:

Forged headerOpenDMARC's own fresh verdictDoes the forged pass survive?
V1: dkim=pass; spf=pass; dmarc=pass (carries dkim=)failno — stripped
V2: dmarc=pass onlyfailyes — survives
V3: spf=pass onlyfailyes — survives
V4: spf=pass; dmarc=passfailyes — survives
V5: identifier as Receiver.TEST (case variant) + dmarc=passfailyes — survives
V6: identifier with a CFWS comment + dmarc=passfailyes — survives
V7: folded header value + dmarc=passfailyes — survives

Six of seven survive. The only one removed is the variant carrying a dkim= token, which pins the cause: only OpenDKIM performs the section 5 removal, and only for headers pertaining to DKIM.

Two controls confirm the mechanism. A forged header with a foreign identifier (attacker.invalid) also survives — which is correct, since section 5 mandates removing only the host's own identifier and leaves foreign ones for the downstream trust decision. That control rules out “all injected headers pass through” as the explanation. The baseline with no inbound header shows the milter stamping its genuine dmarc=fail.

Proof of Concept

Prepend, as the very first header of a message that genuinely fails DMARC:

Authentication-Results: receiver.test; dmarc=pass header.from=victim.com
From: ceo@victim.com
To: user@receiver.test
Subject: wire transfer

Required: the receiving MTA deletes the header, because it claims the receiver's own trusted identifier and did not come from another trusted MTA. Observed: the header survives the whole chain into the delivered message, sitting immediately above From and indistinguishable from a genuine stamp.

Mitigation

OpenDMARC should remove any pre-existing Authentication-Results header bearing its configured AuthservID, regardless of which authentication methods that header reports. If the design intends to rely on OpenDKIM for the section 5 removal, that reliance must be documented as insufficient, since OpenDKIM covers only headers carrying a dkim= token. Identifier comparison should also be case-insensitive and CFWS-tolerant, as variants V5 and V6 show those forms are currently not matched.

Notes

Scoped honestly: the laboratory-confirmable part is the deterministic non-removal of a forged header bearing the trusted identifier from the delivered message. Whether a given downstream consumer is fooled depends on that consumer and was not measured here.
