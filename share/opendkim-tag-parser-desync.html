An RFC-valid exotic i= or d= value desynchronises OpenDKIM's tag parser, yielding permerror and a false header.a=rsa-sha1 in the Authentication-Results header (OpenDKIM ≤ 2.11.0)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDKIM
Source code: https://github.com/trusteddomainproject/OpenDKIM
Affected version: OpenDKIM 2.11.0 (Debian package 2.11.0~beta2-9.1+b1). Rspamd 4.1.2 and dkimpy 1.1.8 are the differential oracles and both handle the same signatures correctly.
Vulnerable component: DKIM-Signature tag-value parsing (RFC 6376 section 3.5) and the algorithm value written into the Authentication-Results header
Vulnerability type: CWE-1286 (Improper Validation of Syntactic Correctness of Input) leading to CWE-393 (Return of Wrong Status Code)
Attack vector: Remote, unauthenticated. One message carrying a cryptographically valid signature made with the sender's own key, using an RFC-valid but unusual i= or d= value. No key material or DNS control of any victim is needed.
CVSS v3.1: 6.5 (Medium) — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:L
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Deterministic across five repetitions, with syntactic controls that pass and report the correct algorithm, three verifiers on the identical message, and a directed accept-direction sweep that never produced a pass.

Impact. A valid rsa-sha256 signature whose i= carries a quoted local part with an interior at-sign is reported as permerror, with the algorithm misstated as rsa-sha1 in a trusted header.

Description

Two consequences, and neither is a spoof.

Interoperability. OpenDKIM rejects RFC-valid mail. Any signer that uses a quoted-string local part in i=, or writes d= with a trailing dot, has its signatures reported permerror on OpenDKIM receivers while Rspamd and dkimpy accept them. Where the sending domain relies on DKIM for DMARC alignment, that becomes a DMARC failure for legitimate mail.

Authentication-Results integrity. The false header.a=rsa-sha1 is written into a header bearing the receiver's own trusted authentication service identifier. RFC 8601 section 2.7.1 defines header.a as the algorithm actually used, and RFC 8301 deprecates rsa-sha1 for DKIM, so any downstream consumer that reads algorithm information out of Authentication-Results — a policy engine that refuses deprecated algorithms, an inventory of algorithm use, a security dashboard — ingests a value with the shape of a downgrade for a message that in fact used SHA-256. Whether a particular consumer acts on it was not measured; the false value itself is deterministic.

RFC 6376 section 3.5 defines the i= tag as an identity whose local part may be a quoted string, and section 3.2 governs the tag-value list in which it sits. A signature carrying i="x@y"@attacker.net, or a d= with a trailing dot, is therefore syntactically valid.

Such a value desynchronises OpenDKIM's tag tokenizer. A cryptographically valid rsa-sha256 signature is reported as dkim=permerror, and the Authentication-Results header OpenDKIM writes states header.a=rsa-sha1 — an algorithm the message never used, and one whose appearance has the shape of a downgrade. Rspamd and dkimpy accept the same signature.

Four trigger forms were confirmed, on a message whose signature is cryptographically valid, with the key for d=attacker.net published and From: a@attacker.net:

i="x@y"@attacker.net     quoted-string local part containing an interior '@'
i=x@y@attacker.net       two unescaped '@'
i=x\@y@attacker.net      backslash-escaped '@'
d=attacker.net.          trailing dot

Three verifiers on the identical message, deterministic across five repetitions:

VerifierVerdictIdentity and algorithm reported
OpenDKIMdkim=permerrorstamps header.a=rsa-sha1, which is false: the signature is rsa-sha256
RspamdR_DKIM_ALLOW, dkim=passidentity attacker.net, taken from d=
dkimpyverify() returns trueAUID domain by the last-@ split is attacker.net, equal to d=, so valid

Controls isolate the cause to a second structural character inside the tag value, rather than to quoting or to the i= tag as such:

Signature tag under testOpenDKIM verdictReported algorithm
i=x@attacker.net (one @, no quoting)dkim=passrsa-sha256, correct
i="xy"@attacker.net (quoted, no interior @)dkim=passrsa-sha256, correct
i="x@y"@attacker.net (quoted, interior @)dkim=permerrorrsa-sha1, false

The false header.a is the direct evidence of the desynchronisation. The value cannot have been read from the message, because the message says a=rsa-sha256; the parser has lost its place and reported a defaulted or stale algorithm instead.

The direction was tested and it is closed. A directed accept-direction sweep placed the offending i= immediately before each critical tag in turn — a=, d=, s=, h=, bh=, b= — and additionally tried a duplicated a=rsa-sha1;a=rsa-sha256, a swallowed and a duplicated d=, a dropped a=, an unterminated quote, and a quote-swallow injection aimed at replacing d=. OpenDKIM returned permerror, or wrote no Authentication-Results at all, in every single case and never returned dkim=pass. That includes a case where the injection did make OpenDKIM read header.d=victim.net: the verdict was still permerror.

Proof of Concept

Publish a key for a domain the sender controls and sign an ordinary message with it:

sel._domainkey.attacker.net.  IN TXT "v=DKIM1; k=rsa; p=<public key>"
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=attacker.net; s=sel;
    i="x@y"@attacker.net; h=from:to:subject; bh=...; b=...
From: a@attacker.net
To: user@receiver.test
Subject: hello

...

The signature is cryptographically valid over these bytes; dkimpy and Rspamd both confirm it. Required under RFC 6376 section 3.5, given that a quoted-string local part is legal and the AUID domain equals d=: dkim=pass. Observed on OpenDKIM:

Authentication-Results: receiver.test; dkim=permerror header.d=attacker.net header.a=rsa-sha1

Both halves of that line are wrong: the signature is valid, and its algorithm is rsa-sha256. Replacing the value with i="xy"@attacker.net, which removes only the interior at-sign, restores dkim=pass with header.a=rsa-sha256.

Mitigation

Correct the DKIM-Signature tag tokenizer so that a quoted string is consumed as a unit, an escaped @ does not terminate a value, and a trailing dot in d= is handled as a fully qualified name rather than as a structural break. Tag values must be delimited by the semicolon and equals structure of section 3.2, not by characters that may legitimately occur inside a value.

Independently of the parse fix, the reporting path must not emit an algorithm it did not read from the signature. If the algorithm cannot be determined, header.a should be omitted rather than defaulted, since a defaulted rsa-sha1 is both false and misleading in the direction of a weaker algorithm.

Notes

This is not a spoof, and the report should not be read as one. The accept-direction sweep described above was run specifically to look for a steerable variant and found none: OpenDKIM never flipped to dkim=pass under any placement or injection tried, including the case where the parser could be made to read a victim domain into header.d. The desync cannot be used to authenticate an identity that should have been rejected. The claimed impact is interoperability plus the integrity of the Authentication-Results value, and nothing more.

The absence of a steerable variant across that sweep is strong evidence but not a proof that none exists; it bounds what has been demonstrated.

Distinct from the other DKIM tag findings in this series, which concern an i= outside d=, the key record's k= tag, and the t=s flag. This one is OpenDKIM's tokenizer losing a tag, which the rsa-sha1 misreport demonstrates directly.
