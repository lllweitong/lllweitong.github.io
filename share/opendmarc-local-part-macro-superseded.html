Superseded: OpenDMARC SPFSelfValidate mishandles the SPF %{l} local-part macro (OpenDMARC ≤ 1.4.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: The Trusted Domain Project
Software: OpenDMARC (SPFSelfValidate)
Affected version: OpenDMARC 1.4.2, built from the upstream tarball rel-opendmarc-1-4-2. The finding was originally isolated on the Debian package 1.4.2-1+deb12u1 and re-confirmed against pristine upstream. Earlier 1.4.x and 1.3.x releases are expected to share the behaviour.
Vulnerable component: SPF macro expansion in SPFSelfValidate — the %{l} local-part substitution. Superseded by opendmarc-spf-postmaster-macro.
Vulnerability type: CWE-20 (Improper Input Validation) - assessed at opendmarc-spf-postmaster-macro, not here
Attack vector: Not assessed separately. See opendmarc-spf-postmaster-macro, which establishes the correct mechanism and the conditions under which it is reachable.
CVSS v3.1: Not assessed separately - see `opendmarc-spf-postmaster-macro`
Status: The observation itself is reproducible and was confirmed with a domain-macro control. Its root cause was subsequently corrected by opendmarc-spf-postmaster-macro, whose query-log evidence establishes the true mechanism.

Impact. Published for completeness and not submitted as a vendor vulnerability: the root cause recorded here was mis-diagnosed and the corrected entry, opendmarc-spf-postmaster-macro, supersedes it and covers the fail-open direction this entry missed.

Description

As framed here, the impact was denial of validation and nothing more: a legitimate sender publishing per-user SPF through %{l} has its own aligned mail mis-failed on OpenDMARC, which under aspf alignment carries into a DMARC failure. The %{s} sender macro follows the same code path.

That account is incomplete. The corrected mechanism additionally yields SPF pass and therefore dmarc=pass on a forged local part whenever the victim's zone resolves at postmaster._spf, which is the direction this entry missed and the reason it should not be read on its own. The full impact statement is in opendmarc-spf-postmaster-macro.

This entry is published for completeness and is deliberately not submitted as a vendor vulnerability, because it has been superseded. Its root cause was mis-diagnosed as “OpenDMARC does not expand %{l}”. The behaviour established later, with the authoritative server's query log as ground truth, is that OpenDMARC always expands %{l} to the literal string postmaster. Readers should go to opendmarc-spf-postmaster-macro, which carries the corrected mechanism and the assessment.

The distinction matters. “Does not expand” implies the term simply never matches, which is a purely fail-closed denial of validation, and that is how this entry framed the impact. Always expanding to postmaster reproduces the same fail-closed observation and opens a fail-open direction, because an A record published at postmaster._spf makes OpenDMARC match and return SPF pass for a forged local part. This entry's framing was therefore incomplete rather than merely imprecise.

What was observed here. With a victim record exists:%{l}.k.probe.example.com, an envelope local part of alice, and the probe node published at the real local part:

Macro under testOpenDMARCRspamd
%{l}, local part alicespf=fail — alice.k.probe... is never matchedspf=pass — queries alice.k.probe...; tracks alice to alice and bob123 to bob123
%{o} and %{d}, the domain macros (control)passpass

The domain-macro control is a consensus, so the gap was correctly localised to the local-part macro letter. That much of this entry stands.

What was wrong. The inference “does not expand” was drawn from a setup in which the A record sat at the real local part, a setup under which non-expansion and expansion-to-a-wrong-value are indistinguishable, because both simply fail to match. Moving the A record to postmaster._spf separates them, and the authoritative server's query log then shows OpenDMARC asking for postmaster._spf while Rspamd asks for alice._spf. A null sender, MAIL FROM:<>, makes both query postmaster._spf, which pins the mechanism further: OpenDMARC applies the null-sender substitution rule to non-null senders.

Proof of Concept

The probe as originally run, retained for the record:

victim.example. IN TXT "v=spf1 exists:%{l}.k.probe.example.com -all"
alice.k.probe.example.com. IN A 203.0.113.9
# MAIL FROM:<alice@victim.example>

Observed: OpenDMARC spf=fail, Rspamd spf=pass. For the reproducer that actually distinguishes the two candidate causes, and for the fail-open case, use the proof of concept in opendmarc-spf-postmaster-macro, which publishes the A record at postmaster._spf instead.

Mitigation

The fix is stated in opendmarc-spf-postmaster-macro: expand %{l} and %{s} from the local part of the checked identity, and substitute postmaster only when the reverse path is null, per RFC 7208 sections 7.3, 2.4 and 4.3. A single change closes both the fail-closed and the fail-open direction, which is a further reason to carry one entry rather than two.

Notes

Why this is not submitted separately. It is the same defect as opendmarc-spf-postmaster-macro, described less accurately. Submitting both would report one code path twice, and the weaker of the two descriptions states a root cause that is not the real one and omits the fail-open direction entirely, which would understate the finding to the vendor. The entry is retained here only so that the correction is visible and the earlier framing is not silently dropped from the record.

The methodological point is worth keeping. A verdict-only differential cannot distinguish “the macro is not expanded” from “the macro is expanded to the wrong value” when the probe node sits at the value the correct expansion would produce, because both fail to match. Moving the probe, and reading the authoritative server's query log rather than the verdict, is what separated them.
