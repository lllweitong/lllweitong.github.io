Rspamd treats a DKIM signature expiry of x=0 as no expiration, so a signature expired at the Unix epoch still verifies (Rspamd ≤ 4.1.2)

Author: Weitong Li, Virginia Tech <weitongli@vt.edu>
Date: 2026-07-31
Vendor: Rspamd project (Vsevolod Stakhov)
Software: Rspamd
Affected version: Rspamd 4.1.2. Originally isolated on 3.10.2 and re-confirmed on 4.1.2 on 2026-07-28. dkimpy 1.1.8 handles the same signature correctly.
Vulnerable component: DKIM signature expiration — the x= tag of RFC 6376 section 3.5 and the expiry comparison performed at verification
Vulnerability type: CWE-347 (Improper Verification of Cryptographic Signature) / CWE-20 (Improper Input Validation)
Attack vector: Remote, but only in the direction the signed scope permits: x= is covered by b=, so the value must have been chosen by the original signer.
CVSS v3.1: 3.7 (Low) — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N
Status: Reproduced on 2026-07-28 against the current release (run 20260728-120957) with a scripted reproducer, negative controls, and a second independent implementation as the differential oracle. Confirmed against dkimpy as the differential oracle, with the neighbouring past values, the future values, and the t=-present, t=-absent and x<t variants all exercised.

Impact. A signature carrying x=0, which expired on 1 January 1970, passes on Rspamd as though the tag were absent, while dkimpy correctly reports it as past.

Description

For a signature carrying x=0, the DKIM validity window never closes on Rspamd. The same wire message continues to pass Rspamd-based filtering indefinitely while every conforming verifier treats it as expired, which is a silent divergence in whether a message counts as DKIM-authenticated, and a defeat of the replay-window control that x= exists to provide.

Exploitability is limited, and the limit is structural rather than incidental. The x= tag sits inside the signed scope, so an attacker cannot set x=0 on somebody else's signature without invalidating b=. The bug bites when the original signer emits x=0, whether through an off-by-one in expiry arithmetic, an uninitialised field, or a deliberate but mistaken use of zero as a “no expiry” value. In that case Rspamd alone keeps honouring the signature for ever, including for a captured message replayed long after the signer intended it to lapse.

RFC 6376 section 3.5 defines x= as an absolute Unix timestamp giving the signature's expiration, states that the signature is invalid if the verification time is past it, and adds that a signature whose x= is less than its t= is invalid on that ground as well. The value is an ordinary integer; the specification defines no sentinel meaning for zero.

Rspamd treats x=0 as though the tag were unset, guarding the expiry comparison with a test for a non-zero value. A signature that expired at the Unix epoch is therefore accepted as current, and returns R_DKIM_ALLOW. dkimpy rejects the same signature with ValidationError: x= value is past (b'0').

Only the x= value varies across the sweep:

The second row is what turns the observation into a bug claim rather than a general absence of expiry checking. Rspamd does implement the expiry comparison and does suppress every other past timestamp, including the value 1, one second later than the failing case. Only zero is exempt, which points at a zero-guard around the comparison rather than a missing comparison.

The result is robust across the surrounding variations. It holds with t= present, with t= absent, and in the x < t configuration, where the test signature carried x=0 alongside t=1781531772 and is therefore invalid twice over under section 3.5. No Y2038-style wrap was observed on Rspamd: x=2^31 and x=2^32 are accepted as far-future values, as they should be, and values at or above 2^63 are dropped. dkimpy uses arbitrary-precision integers throughout and shows no boundary effect at all.

Proof of Concept

Publish an ordinary key record:

sel._domainkey.signer.example.  IN TXT "v=DKIM1; k=rsa; p=<base64 RSA public key>"

Sign the message with the matching private key, with an expiry at the Unix epoch. Both t= and x= are inside the DKIM-Signature header field and are therefore covered by b=:

DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=signer.example; s=sel;
    t=1781531772; x=0; h=from:to:subject:date; bh=<body hash>; b=<signature>

Required under RFC 6376 section 3.5: the verification time is past x=0, and x is additionally less than t, so the signature is invalid on two counts. Observed on Rspamd: R_DKIM_ALLOW. Observed on dkimpy: ValidationError: x= value is past (b'0').

Re-sign with x=1 and Rspamd suppresses the signature as expired, which isolates the value zero as the whole of the divergence.

Mitigation

Treat x=0 as the past timestamp it is, not as a sentinel for an absent tag. The distinction the verifier needs is between an x= tag that is present and one that is absent, which is a question about the tag list and not about the value, so the zero guard around the expiry comparison should be removed. Independently, enforce the section 3.5 rule that a signature with x less than t is invalid, which would also catch this case.

Notes

The differential oracle for this finding is dkimpy. OpenDKIM was not exercised on the x= vein, so no claim is made here about its handling of an epoch expiry.

The zero-guard described above is inferred from the behaviour, in that every other past value is suppressed and only zero is exempt. The corresponding code in Rspamd's DKIM module has not been identified, and confirming it upstream remains an open step. No line number or function is asserted.

Distinct from the other DKIM entries in this group, which concern key-record tags. This one is a signature tag, x=, in section 3.5, and no other finding in the set covers signature expiration.
